# The loop

The tracker is the queue, and the loop turns each ready ticket into one pull request. A small dispatcher reads the queue every few minutes and starts a worker for each ready ticket while a slot is free. A worker builds one ticket as its own process: it starts an agent, pushes the work, opens the pull request, and waits for the shared merge gate on GitHub. A red gate, also a red fuzz check, goes back to the agent with what failed, and the blast level decides whether a green pull request merges at once, after a hold, or once the owner marks it ready. No model decides what runs next or whether a ticket passed: the queue's order decides what starts, the gate decides, and GitHub merges. The loop runs no gate, no code review, no UI review, no landing, no Epic branch, and no Epic pull request of its own.

This file is the one home of the fixed design. The `loop` command, from `loop/` in the agent-workflow repo, is the script for every repo. A repo's `loop.toml` holds the values the script reads, and its `docs/agents/loop.md` links here and holds the rest of its settings.

## Fixed design

Every repo keeps these rules. Change a rule here, on purpose, and give the reason in the pull request.

1. **Queue.** `loop start` starts the dispatcher (The dispatcher), which reads the tracker with `[queue] filter` (Queue) every `poll_minutes` and starts a worker (The unit of work) for each ready ticket, in the filter's order, Jira priority then key by default, while a slot is free. A ticket is ready when it carries the repo's Jira component, `component` (Tracker), is not an Epic, is not Flagged, has no active unit, its pull request has not merged, and each of its blockers is done or merged. A ticket whose blocker has an open pull request waits: a branch always starts from the head of `main_branch`, and a pull request always targets it. A ticket is merged when a pull request of its branch has merged on GitHub. A ticket of another component, `manual` included (Human steps), or with no component is never a candidate, so it is never built, flagged, or refused, and counts only as a blocker, through its status in the tracker. An Epic whose tickets change two repos is built by the dispatcher of each. The tracker, GitHub, and the logs (rule 11) hold all state.
2. **Worktree and branch.** Each ticket gets a worktree in the run's state folder and the branch `feat/<KEY>-<slug>`, or `fix/` for a Bug, from `origin/<main_branch>`. A branch of the key that is already on the host or on origin is used again. A ticket whose blocker has an open pull request stacks on it: its branch starts from that branch, and its pull request targets it. The ticket file, `ticket.md` in the ticket's run folder, holds the ticket text, the comments on the ticket, oldest first, and a Loop section: the Epic, the branch and the commit scope, the base it stacks on, the run folder, that the loop pushes and opens the pull request so the agent does neither, and that the gate runs every check so the agent runs the tests that cover its change. `agent_hint` adds a line to it. When `loop.toml` has `setup`, a command list such as `["make", "loop-deps"]`, the script runs it in the worktree after `git worktree add` and before the build, so the agent's first test run finds the repo's packages, and logs a `worktree` `setup` line. A restart runs it again when its earlier setup did not pass. A setup that exits non-zero or runs past `agent_timeout_minutes` makes the ticket stuck (rule 7), with the last 20 lines of its output, `SETUP_TAIL` in [`run.ts`](../../loop/src/run.ts), as the reason. With no `setup`, the script runs nothing.
3. **Agent run.** The script runs each session through the Claude Agent SDK, in [`agent.ts`](../../loop/src/agent.ts), with `/implement` and the ticket file as the prompt.
   - Every process the loop starts, the agent's Claude Code among them, starts through one function, `spawnGroup` in [`spawn.ts`](../../loop/src/spawn.ts), in a process group of its own, with `/dev/null` as stdin. At its limit, which is the agent timeout for a session, the script sends SIGTERM to the whole group, then SIGKILL to what still runs a minute later. The page opener of rule 12 does not, because the script does not wait for it.
   - No session gets background tasks (`CLAUDE_CODE_DISABLE_BACKGROUND_TASKS`), and the settings deny the tools that wait for a later turn, such as `ScheduleWakeup`, `CronCreate`, and `Monitor`. A session ends at its status, and nothing wakes it later.
   - The permission mode is `auto`, and the auto mode classifier learns that an unattended loop runs the session and owns each worktree under the state folder. Nobody answers a prompt, so a routine action that auto mode denies can block a ticket.
   - The system prompt is Claude Code's own, with [`dispatch.md`](../../loop/src/dispatch.md) added: the rule for when to hand work to the subagent tiers that `install.sh` links from [`agents/`](../../agents) to `~/.claude/agents`. `worktree.baseRef` is `head`, so a `trial` worktree branches from the ticket's last commit.
   - The model and effort are those of `[agent]` (Agent), so no session takes them from the host's own Claude Code settings.
   - Each session gets the run's environment, which holds every secret (Secrets) but not the machine token, `LOOP_RUN_DIR` set to the run folder, and the env of its stack slot (Stack per worktree).
   - Each SDK message goes to `agent-<n>.jsonl` in the run folder as it comes, and the stderr of Claude Code to `agent-<n>.err`, so a run can be followed while it lasts.
   - The output schema returns `status` (`done` or `blocked`), `reason`, `decisions`, `notes`, and `blast` (`green`, `yellow`, or `red`, green when left out), which `implement` fills from the blast-radius skill. `decisions` holds only an open question that the ticket and the docs do not answer and that only KC can settle, and it is usually empty. The script takes the status from the result message. A session that returns no status, fails, or runs past its limit fails the build.
   - A fix attempt and a session that goes on after a usage limit resume the same session. The script resumes only a session that started in the same run, after the ticket's last `start` line, so a restart starts a new session (rule 9).
4. **Push and pull request.** After a `done` build with a new commit, the script pushes the branch. On the first push it opens the pull request, or takes the open one of the branch: the title `feat(<KEY>): <summary>`, or `fix(`, which becomes the squash commit on main, and a body that the gate's fuzz job reads as the intent: a first line that links the ticket and names the spec, `Spec: [<path>](<link>)`, from the Markdown file of the repo that the Spec line of the Epic's description links, or the first one of the repo it links, where the repo is that of a merged pull request or of the origin remote, or `Spec: <path>` from a line of the ticket that names one, or no spec; then the agent's `reason`; then the ticket text under `## Ticket`. The script writes the body, `pr-body.md` in the ticket's run folder, each time it opens a pull request, so a file of an earlier run never holds a stale ticket text. The agent's `decisions` go on the `pr` log line, not in the body, where a list of decisions reads as a list of blockers. Auto-merge stays off until the checks are green and the blast level lets it (rule 6). A worker's red pull request opens as a draft, and the worker labels it `blast:<level>` when it opens it and after each push (Blast radius). The ticket then goes to the review status (Status and stuck marker).
5. **Wait and fix.** The script polls the checks of the pull request with `gh` every 30 seconds, `LOOP_POLL_SECONDS`, for up to `WAIT_MINUTES` in [`run.ts`](../../loop/src/run.ts), 120. Only the required checks count, from `gh pr checks --required`, so a check that branch protection does not require never makes the gate red. That command lists a check only once it reports, so the script reads the required check names of `main_branch` from branch protection once per run, logs a `required-checks` line, and counts a required name with no check yet as pending. A branch with no protection requires none. A check counts once the pull request's head is the pushed commit. A merged pull request is green. A failed or cancelled check is red. A draft pull request is a pause: the script logs one `wait` `held` line and waits for the draft to go, and the wait's limit does not run while it stays. When the pause ends with auto-merge on, the script turns auto-merge on again, because GitHub turns it off on a draft and does not turn it back on, and merges the pull request itself when that fails. With auto-merge off, every check passing or skipped is green. A red gate resumes the session as a fix attempt, with one message: the end of each failed job's log, the last `LOG_TAIL_LINES` (80), and the findings of the gate's fuzz comment at the head. The `fuzz-report` job posts that comment after the fuzz check ends, so when the fuzz check is red the script polls for it up to `FUZZ_COMMENT_POLLS` (6) times in [`run.ts`](../../loop/src/run.ts), and says so in the message when none comes. The fix commits, the script pushes, and the gate runs again. A fix that returns `done` with no new commit counts as an attempt too: the script runs the failed Actions jobs again on the same head with `gh run rerun --failed`, logs a `rerun` line, and reads the gate again, with each check that runs again pending until its new job reports. Green merges, and red again ends the attempt. After `fix_attempts` fix attempts the gate is still red, the ticket is stuck. A closed pull request and a wait past its limit stop the ticket. A pull request that GitHub reports as `CONFLICTING` with its base runs no check, so the wait reads it as red at once, with the detail `It conflicts with <base>.`, and the fix attempt resumes the session with one message: rebase on the base, resolve, and run the tests that cover the change. The script pushes, and the gate runs again. A semantic clash that passes alone is the nightly suite's to catch.
6. **Hold, merge, and stack.** On the first green, a worker's yellow pull request holds, and the worker hands the ticket back until the hold is over (Blast radius). Then the script turns on auto-merge as a squash, and waits on the checks again with it on, since a required check may not have reported yet. GitHub merges the pull request when every required check passes, and a red check gets a fix attempt (rule 5). When auto-merge does not turn on, the script logs an `auto-merge` line with the reason and merges on the green it has. After each merge, also of a pull request that merged before the run, the script moves the ticket to `Done`, `DONE` in [`epic.ts`](../../loop/src/epic.ts), unless it is already done, and logs a `tracker-status` line. A failed transition logs `fail`, and the run goes on. Then each open pull request that targets the merged branch targets `main_branch`, because GitHub retargets it when the branch is deleted, and the script retargets it itself when GitHub did not. Then the script removes the ticket's worktree and local branch and logs a `worktree` line. A ticket that stops keeps both for its restart. A stacked ticket whose gate is green waits until its pull request targets `main_branch` before the hold and auto-merge, so GitHub never merges it into its blocker's branch. When its blocker stops instead, it stops too.
7. **Stuck.** The script comments on the ticket the fingerprint `Stuck: <step> <result>` as the first line, such as `Stuck: build blocked`, `Stuck: wait red` for exhausted fix attempts, `Stuck: setup fail`, `Stuck: slot taken`, or `Stuck: stop loop-error`, then the reason, the pull request, and the log path on the host, sets the Jira Flagged field, and notifies. A comment that is already on the ticket is not posted again. The other workers keep running. Tickets downstream of a stuck one wait. KC gives a stuck ticket a new start by removing its flag, and the dispatcher starts it at its next poll. `loop stop <KEY>` flags its ticket with the comment `Stopped by the owner` (rule 12).
8. **Limits.** `parallel` tickets build at once, each in its own worktree and stack slot. The dispatcher counts stuck workers in a row, and at `circuit_breaker` it logs `circuit-breaker` `open`, notifies, and starts no worker until a ticket of the row is no longer Flagged, when it logs `circuit-breaker` `closed`. A usage limit that resets within `MAX_USAGE_WAIT_SECONDS` in [`run.ts`](../../loop/src/run.ts), 6 hours, pauses the worker: it waits until a minute after the reset that the session's `rate_limit_event` gives, logs `usage-pause` `ok` with `resumes`, and resumes the session. The dispatcher reads that line and starts no worker until `resumes`, with a `hold` `usage-pause` line. A limit with no reset time, or a later one, hands the ticket back with no flag, and the dispatcher starts no worker for `MAX_USAGE_WAIT_SECONDS`, with a `hold` `usage-limit` line, and notifies once.
9. **Restart.** A ticket is a fixed list of steps: build, push, pull request, wait, merge. A run or a restart starts each ticket at its first step with no pass at the branch's HEAD. A worker's ticket with an open pull request is the one exception, and starts at the wait (The unit of work). A ticket whose pull request merged before the run is merged, and is not built again. A ticket with an earlier start line starts as a restart, on the same worktree, branch, and pull request, with a new session and the prompt `/implement` on the current `ticket.md`, so the agent builds to the ticket text as it is now and not to the scope of the session before. When the pull request is open, the script replaces the `## Ticket` section of its body with the current ticket text, keeps the rest, and logs a `pr-body` line, so the gate's fuzz job reads the ticket as it is now. The script counts the fix attempts from the log, since the ticket's last `start` line, so a restart starts at 0. A push, a `gh` call, and a Jira call change nothing when they run again, so a step that runs again repeats no side effect. A kill between a merge and its retarget or its worktree removal is finished at the next start.
10. **Epic complete.** Only the dispatcher completes an Epic, so two merges never archive at once. After each poll it runs the Epic check, in [`epic.ts`](../../loop/src/epic.ts), for the parent of each ticket whose worker merged since the last poll, and once an hour for every open Epic with a child of the repo's component, so an Epic whose last child is a `manual` step that a person set Done closes too. When the Epic is open and every child of the Epic, of every component, as the tracker gives them then, has merged or is done, the check archives the spec, in [`archive.ts`](../../loop/src/archive.ts), then moves the Epic to `Done`, `DONE` in [`epic.ts`](../../loop/src/epic.ts). The spec's repo is the one that the first link of the Spec line of the Epic's description names, else this repo, that of a merged pull request or of the origin remote. When it is another repo, the check clones it with `gh repo clone` into `repos/` in the state folder, or fetches the clone it made before, and archives there, with the clone's default branch as `<main_branch>`. A spec can be linked by an Epic in each project: the archive finds every Epic whose description links the same spec, and when one of them is not Done, the spec stays on main, with an `archive` `waiting` line, and the completion of the last one archives it. Each link of each such Epic's description of the form `<repo>/blob/<ref>/<path>.md`, where `<repo>` is the spec's repo and `<ref>` is not a commit SHA, changes to link the head of `origin/<main_branch>`, in its text and its target, so git keeps the spec. When a linked path is still on `origin/<main_branch>`, the check deletes the paths on the branch `docs/<Epic key>-archive-spec`, in a worktree of `origin/<main_branch>` in the state folder, pushes it, opens a pull request with the title `docs: archive the spec of <Epic summary>` and the pinned links in its body, and turns on auto-merge. The title has no key, so its merge moves nothing in Jira. An open pull request of that branch is used again. The log gets an `archive` line with the result `pr-open`, `archived` when no path is left on main, `waiting`, `no-spec` when the description links no spec of the spec's repo, or `fail`, then a `complete` line, and the dispatcher notifies. The Epic does not wait for the archive pull request, which merges on its own once its gate is green: the `complete` line names it while it is open. A failed archive leaves the Epic open, so the next check tries again.
11. **Log.** One JSONL line per step in `decisions.jsonl`, with `time`, `epic` (the run's name: the key, or `filter-<hash>` for a filter), `ticket`, `step`, `result`, `commit`, `session`, and `detail`, in [`log.ts`](../../loop/src/log.ts). The steps are `start`, `frontier`, `build` (`started`, then `pass`, `fail`, or `blocked`, or `skipped` when a worker starts again at the wait), `hand-back` (`usage-limit`, `red`, or `hold`), `agent`, `push`, `rerun`, `blast` (the level), `pr`, `pr-body`, `label` (`ok` or `fail`), `draft` (`ok` or `fail`), `hold` (`set`, `over`, or `fail`), `wait`, `base`, `merge`, `retarget`, `stuck`, `required-checks` (`ok` with the names, or `fail`), `auto-merge` (`fail`, when it does not turn on, or `off`, when the blast level rose), `worktree` (`setup`, `removed`, or `fail`), `tracker-status`, `slot`, `meter`, `usage-pause`, `circuit-breaker`, `archive`, `complete`, `notify`, `stop`, and `finish`. The run's `start` line adds `input`, the `pid`, and `setup`: the `claude` version, and the model and effort of the head agent, of each subagent tier, and of the gate's fuzz job, so two runs can be told apart. The `frontier` line adds `summary` and `tickets`, each with its key, summary, status, state, and blockers. A ticket's `start` line adds `slot`, and `base` and `pr` when it stacks. A `build` `started` line adds `attempt`. The `detail` of a `build` `pass` or `blocked` line is the agent's `reason`, and of a `fail` line why it failed. A reader treats a missing `detail` as absent, as on a `pass` line from before it carried one. The `pr` line adds `pr` and `auto_merge`, and `decisions` when the agent returned any, and the `wait` line (`held`, then `green`, `red`, or `timeout`) adds `checks`, each with its `name`, its `bucket`, and its `link`, the URL of the check's run from `gh pr checks`, so the watch page shows each pull request and its checks with no call to GitHub. A reader treats a check with no `link` as one with none. Each `agent` line adds `usage`, from the session's result message: `total_cost_usd`, `num_turns`, `duration_ms`, the subagents by type, the usage of each model, and `peak_context`, the largest context that one of the session's own assistant messages sent. A resumed session reports its whole cost so far, so the last agent line of a session holds its total. Each agent line adds `plan`, the Claude plan meter over the session from its `rate_limit_event` messages: for each of `five_hour` and `seven_day`, the first and the last utilization as `start` and `end`, and `resets_at`. While a session runs, the script logs a `meter` line with the newest reading of each window when it changed, at most once a minute, `LOOP_METER_SECONDS`. The meter belongs to the account, so parallel runs and KC's own sessions move it together, and `loop report` counts it per run. Each reader skips a line that does not parse. The dispatcher's log is `decisions.jsonl` at the top of the state folder, with the run name `dispatch` (Logs), and its steps are `start`, `queue` (`ok` or `held`), `worker` (`started`, `fail`, then `merged`, `stuck`, `handed-back`, `usage-limit`, `stopped`, or `gone`), `hold` (`usage-pause` or `usage-limit`, with `until`), `circuit-breaker` (`open` or `closed`), `archive`, `complete`, `poll` (`fail`), `notify`, and `stop`. A worker's log is `tickets/<KEY>/decisions.jsonl`, and its `epic` is the key. Its own lines, `start` `ok`, `required-checks`, `frontier`, `finish` (`ok`, `stuck`, or `handed-back`), `stop`, and `notify`, carry the ticket's key too, so each adds `run: true`, and a reader of a log with such a line takes the lines without it as the ticket's. Its `start` `ok` line adds `slot`.
12. **Host.** The dispatcher and each worker are systemd user units, so systemd knows whether each is alive, and each outlives the agent or shell that starts it. [`units.ts`](../../loop/src/units.ts) holds the unit settings.
    - `loop start` first fast-forwards the loop's own checkout of agent-workflow to `origin/main`, so every host runs the merged loop, and refuses with git's message when a change that is not committed overlaps the new commits. A checkout on another branch runs as it is. It then loads `loop.toml`, prints a warning for each key the loop dropped, and refuses with one line when the host has no token file, when Secrets Manager lacks a secret the loop needs, which it names (Secrets), or when the dispatcher is active, and names its unit. `loop start <KEY>` and `loop start --filter` are gone, and print so.
    - It starts `loop dispatch` as the transient unit `loop-<name>-dispatch`, with `systemd-run --user --collect --service-type=exec`, `KillMode=control-group`, and `TimeoutStopSec=10min`, and returns when the unit runs. A worker's unit is started the same way. The unit loads the host's token file with `EnvironmentFile=` and runs `bws run -- exec '<loop>' 'dispatch' …`, so the process gets every secret as an env var. `bws` joins its arguments into one `sh -c` line, so each word is quoted, and `exec` makes the loop the shell's own process. `bws` is the unit's main process and passes no signal on, so `KillMode=control-group` sends the SIGTERM of a stop to every process of the unit. The unit gets `PATH`, `HOME`, `LANG`, and `SSH_AUTH_SOCK` from the shell that starts it, because the user manager's own environment differs between a desktop login and a boot with linger. `--collect` unloads the unit when it ends, also when it fails, so a failed worker never blocks the next start. The unit's journal, `journalctl --user -u loop-<name>-<run>`, holds its output.
    - It then starts `loop watch` (Logs) as the user service `loop-watch-8790`, under `bws run` in the same way, so it knows the values to mask, when it is not active, and restarts the service when it took new commits. The service restarts after a crash. One page serves every project on the host. On a host with a screen, it opens the page, and it prints the page's tailnet address, which opens on any device in the tailnet.
    - The run refuses to start when `git`, `gh`, `claude`, `systemd-inhibit`, a command of `tools`, or `docker` for a repo with a stack is not on the PATH, or when its env lacks a secret. It holds off sleep with `systemd-inhibit`, which runs beside it, so the run stays the process that `bws run` started.
    - `loop stop` stops the dispatcher, then each worker unit of the repo, and flags nothing, so the next `loop start` goes on with the same tickets (rule 9). `loop stop <KEY>` comments `Stopped by the owner` on the ticket and flags it, then stops its worker, so the dispatcher never starts it again until KC unflags it. A worker takes the SIGTERM as a stop: it logs `stopped`, ends every agent session through the process function (rule 3), frees its slot, and notifies. The step in progress writes no result, and no `finish` line follows. Systemd kills what still runs after 10 minutes. `loop stop --filter` is gone, and prints so.
    - `loop ticket <KEY>` is a launcher like `loop start`: it updates the checkout, then refuses with one line a ticket whose unit `loop-<name>-<KEY>` is active, one that is Flagged, of another component, or with no component, which it reads in Jira with the secrets that `bws secret list` gives, and a start with no free slot. It takes a slot as the dispatcher does (The unit of work), and starts `loop run-ticket <KEY> --slot <n>` in that unit. `loop run <KEY>` and `loop run --filter <JQL>` build an Epic or a filter in the foreground for the scenario tests; no command starts them in a unit, and they complete no Epic (rule 10).
    - An agent starts the loop only with `loop start` or `loop ticket`, because the Bash tool stops a command after 10 minutes.
13. **Main.** The loop never writes to `main_branch`. Work reaches it only through a pull request that the gate passed, and a merge to main is not a release.

## The unit of work

One ticket is the unit of work, so one bad ticket never stops the rest. The dispatcher, or `loop ticket <KEY>` by hand (rule 12), starts a worker, `loop run-ticket <KEY> --slot <n>`, in the unit `loop-<name>-<KEY>`, the same unit for both, so a ticket never builds twice at once. The code is the `run-ticket` mode of [`run.ts`](../../loop/src/run.ts), the slots are [`slots.ts`](../../loop/src/slots.ts), and the folders are [`layout.ts`](../../loop/src/layout.ts).

- **Slot.** A slot is the folder `slots/<n>/` of the state folder, which holds the key of its ticket and the name of its unit. A launcher, the dispatcher or `loop ticket`, takes a slot only while fewer than `parallel` are held, and takes the first of slots 2 to `parallel + 1`, then of the spare slots after them, that `mkdir` creates and whose ports no other Compose project holds, from `docker ps` read before the start (Stack per worktree). `mkdir` is atomic, so two launchers never take the same one. A slot older than a minute whose ticket has no active unit is free: the dispatcher frees each such slot at each poll, and a launcher takes one back, by renaming it to a name of its own before it removes it, so of two launchers that find it left behind, one takes it back. The worker frees its slot at its end, also on a stop or a throw.
- **State.** A ticket's folder is `tickets/<KEY>/` under the state folder: `ticket.md`, `pr-body.md`, `worktree/`, `agent-<n>.jsonl`, `agent-<n>.err`, and `decisions.jsonl`, with the key as the run name (rule 11). The watch page reads it as a run named by the key: its log, its ticket detail, its files, and its agent feed. It never lists or serves `worktree/` or the log file.
- **Steps.** The worker builds the one ticket: worktree, setup, build, push, pull request, wait, fix attempts, the blast level and its hold (Blast radius), merge, status, and worktree removal. The branch always starts from the head of `main_branch`, and the pull request always targets it: a worker never stacks. The fix attempts, the usage pause, the timeout, and the process group rules stay, per ticket. A Bug's `ticket.md` adds one line to its Loop section: reproduce first, the acceptance test of the first "What the user sees" line fails twice on the stack before the fix. Its branch and title carry `fix` (rule 2).
- **Endings.** A worker ends in one of three ways, and logs its own `finish` line with the result. Merged: the ticket is Done, and the exit code is 0. Handed back: a usage limit the loop does not wait for, a red pull request, or a yellow one's hold, with a `hand-back` line whose result is `usage-limit`, `red`, or `hold`; the ticket keeps its status and gets no flag. Stuck (rule 7): a failed or blocked build, a failed push or pull request, exhausted fix attempts, a timeout, a closed pull request, a pull request that did not merge, or a throw of the worker, which logs `stop` `loop-error` first. A stuck worker comments the fingerprint and the reason, sets the Flagged field, and notifies, and nothing starts the ticket again until KC unflags it.
- **Restart.** An unflagged ticket starts again on the same worktree, branch, and pull request (rule 9). With its pull request open, it starts at the wait, logs `build` `skipped`, and moves the ticket to the `tracker.landed` status, with no build; a red gate then gets a fix attempt in a new session. A ticket whose pull request merged is moved to Done and not built.

## The dispatcher

The dispatcher, `loop dispatch` in [`dispatch.ts`](../../loop/src/dispatch.ts), is the unit `loop-<name>-dispatch` that `loop start` starts (rule 12). It never waits on a person and never builds: at each poll it reads how each worker that ended did, from the worker's own log, then reads the queue (rule 1), starts a worker for each ready ticket while a slot is free, and runs the Epic check (rule 10).

- **Skips.** A ticket whose unit is active, by name, is building, and is skipped, so a hand start and a dispatcher start never build one ticket twice.
- **Slots.** The dispatcher owns the slots (The unit of work): before a start it reads `docker ps` and takes the first free slot whose ports no other Compose project holds, and a slot frees when its unit is no longer active.
- **Handed back.** A ticket whose open pull request is a draft, carries the `hold` label, or has a `Hold until` time still ahead is not ready, so a handed-back ticket starts again when the owner marks it ready, removes the label, or the hold ends.
- **Holds.** The circuit breaker and a usage limit stop new starts (rule 8). The workers that run go on, and the dispatcher keeps reading the queue, checking the Epics, and reading how each worker ended.
- **Stop.** A SIGTERM ends the dispatcher with a `stop` `stopped` line. It stops no worker: `loop stop` stops each one after it.

## Settings

Each section names what it settles, and its `loop.toml` key when the script reads one. A repo's `docs/agents/loop.md` keeps these headings. A value with a key lives in `loop.toml` only, and the repo doc points there; the doc holds the values the script cannot read. A key that the old loop read and this one dropped, `[gates]`, `[acceptance]`, `[ui]` `skill`, `[ui]` `blocking`, `[demo]`, `[tracker]` `name_landed_keys_only`, and `[review]`, prints a warning that names it and is ignored. Any other unknown key refuses the file.

The machine README, `~/dev/machines/README.md`, holds how to reach each machine and how secrets get onto it. Secrets and Hosts link to it.

### Run

Settles who starts the loop, and where. The command is `loop start` in the main checkout, which starts the dispatcher, and `loop stop` stops it with every worker (rule 12). An Epic whose tickets change more than one repo is built by the dispatcher of each, and each builds only its repo's tickets (rule 1). Each host knows only its own units, so a person runs a repo's dispatcher on one host at a time.

### Tracker

Settles the tracker and how the Epic's children and blocking edges are stored. `[tracker]` gives `kind` and `url`. Jira is the only adapter. It reads the children of an Epic as the issues with `parent = <Epic key>`, and a blocking edge as a "Blocks" issue link. It signs in with basic auth, the account email and an API token without scopes, on the site URL. It marks a stuck ticket with the Jira Flagged field, so the site needs that field. Each ticket's Jira component names where its work happens: the repo it changes, or `manual`. The top-level `component` gives the component of the repo's tickets, and defaults to `name`.

### Status and stuck marker

Settles which status changes the loop makes and how a stuck ticket shows. `tracker.in_progress` is the status of a ticket that starts, and `tracker.landed` the status of a ticket whose pull request opens. Each must match a status name of the workflow exactly, and the workflow must offer a transition to it from the status that a ticket has at that point. The loop, not the tracker's automation, sets a ticket's done status, `Done`, when its pull request merges (rule 6), and sets `Done` on the Epic at its last merge (rule 10).

### Human steps

Settles what only a person can do, and how tickets carry it. A step only a person can do is a ticket with the Jira component `manual`. No loop builds or flags it. The person sets it `Done`, and a ticket that waits on it starts at the next run (rule 1).

### Branches and commits

Settles where the key goes in commits. The script names each branch `feat/<KEY>-<slug>`, or `fix/` for a Bug, and each pull request title `feat(<KEY>): <summary>`, which the squash merge makes the commit on main. `main_branch` names the branch each pull request targets, unless it stacks.

### Gate

Settles the checks that decide a pull request. The shared merge gate, `.github/workflows/gate.yml` in agent-workflow, runs the repo's `make check` with `gate / fuzz` beside it; `setup-repo` puts a repo on it and requires the two alone. A check decides a merge, and the fuzz check fails only on a reproduction that fails on rerun. The fuzz job runs adversaries against the pull request with the ticket text as the intent, keeps a finding whose reproduction fails again on the head, with each adversary's edit and new file taken out but the reproductions, runs `[fuzz] setup` again before the head rerun, so it meets a fresh stack, and again on the base before the base run, where a failed setup makes each finding new, compares the two outputs with only colour codes, the checkout's path, temp names, memory addresses, and a test runner's timings masked, drops a finding with no title, command, or reproduction, and kills a reproduction's process group after `FUZZ_RUN_SECONDS` (600), marks one that fails the same way on the base as pre-existing, writes one review comment, and fails on a new finding. The fuzz job holds no token that can write, and its `fuzz-report` job, which runs none of the pull request's code, posts the comment. A docs-only pull request skips it. `agent_hint` adds a line to each ticket file for what the gate does not say, such as what the tests need from the stack. The `[fuzz]` table holds settings of the gate, which `actions/fuzz/action.yml` reads from the base branch: `enabled` (true), `model` and `effort` (the gate's inputs), `adversaries` (3), `blocking` (true; false posts the findings and passes), `setup` (a command that brings up and seeds the stack, none by default), and `skip` (path globs). The script checks their types, logs the fuzz job's model and effort in `setup`, and uses none of them. A draft pull request does not merge, and the script waits with it (rule 5).

### Blast radius

Settles how a worker's pull request merges. `[blast]` gives `red` and `yellow`, each a list of path globs, empty by default, and `hold_minutes` (60). After each `done` build, before the push, the worker takes the highest of the level before, the level of the globs that a changed file of the branch matches, and the agent's `blast`, logs a `blast` line, and labels the pull request `blast:<level>`. The changed files come with no rename detection, so a file moved out from under a glob counts, and a glob's `*`, `**`, `?`, `[...]`, and `{a,b}` match a name that starts with a dot too. A level never goes down. A level that rises while auto-merge is on turns it off before the push and logs `auto-merge` `off`. A restart at the wait takes the highest of the label, the log's `blast` lines, and the globs, labels the pull request again, since a worker that died before its label went on left only some of them, and reads from GitHub whether auto-merge is on. When it is on and the level is not green, a worker that died after the level rose left it on, so the restart turns it off and logs `auto-merge` `off`, and the wait turns it on again once the level lets it. Red: the pull request opens as a draft, or turns into one when the level rises to red, before its label, and the worker logs `draft` `ok` and hands the ticket back; once the owner marks it ready, the dispatcher starts it again at the wait. A restart that finds a red pull request that is not a draft, and whose timeline has no `ready_for_review` after its last `convert_to_draft`, makes it a draft and hands back again. Yellow: at the first green the worker writes `Hold until <time>` in the `## Loop` section of the body, logs `hold` `set`, and hands the ticket back; after the hold the worker turns auto-merge on, unless the `hold` label is on or it is a draft, when it hands back again. Green: auto-merge turns on at the first green. The gate labels nothing, and a pull request the loop did not open has no level.

### Stack per worktree

Settles how two tickets run full stacks side by side. `[stack]` gives the base `ports` and the `port_step` per slot. A repo with no stack leaves it out.
Slot 0 is the main checkout, so a person's own stack keeps the base ports, and slot 1 stays free, so the tickets in flight use slot 2 and up. For each key under `ports`, the script sets an env var of that name to the slot's port, and sets `COMPOSE_PROJECT_NAME` to `<name>-<key>`, and the repo's Compose files and dev server configs read them. The agent starts and stops its own stack. Before each session, the script reads `docker ps` for the containers of other Compose projects, such as a stack from a session outside the loop. When one holds a port of the slot, the slot moves to the first free one of `SPARE_SLOTS` in [`slots.ts`](../../loop/src/slots.ts), 8, after the ticket slots, for the rest of the run, and the script logs a `slot` line with the container. With no spare slot free, the ticket is stuck, and the reason names the container.

### UI review

Settles the UI paths. `[ui]` gives `path`, one folder prefix of the UI, and `accepted_unchecked`, phrases for the parts that a review is known not to check. The script checks them and uses none of them. The owner reviews the look of the UI on staging. A repo with no UI leaves it out.

### Agent

Settles what the head agent runs on. `[agent]` gives `model` and `effort`, and the defaults are `claude-opus-5-5` and `high`. Effort is the setting to change to cut cost: at every cost, Opus 5.5 scores at or above Sonnet 5.5. Each turn sends the whole context again, so the cost of a ticket grows with how large its sessions get, and `loop report` shows each session's peak context. `setup` prepares each new worktree before the build (rule 2), and has no default.

### Connectors

Settles which MCP servers the agent gets. The script passes no MCP configuration of its own. Each server adds its tool names and instructions to the context of every turn, and the ticket file already holds the ticket text, so a run needs no tracker connector.

### Notifications

Settles the channel, the events, and what a message may contain. `notify.url` is the ntfy server, and the `NTFY_TOPIC` secret is the topic. The events are a stuck ticket, `<KEY> stuck`; a pause, `<run> paused`; a usage limit that stops the run, `<run> stopped at a usage limit`; a stop, or a failure of the loop itself, `<run> stopped`; an Epic complete, `<Epic key> complete`; and the finish, `<run> finished.` with what it merged and stopped. A message holds keys and statuses only. Anyone who knows the topic can read the messages, so the topic is a secret.

### Secrets

Settles which secrets the loop needs and where each one lives. Each secret lives once, in Bitwarden Secrets Manager, under its env var name. `secrets` in `loop.toml` lists the names, and is empty by default. The script needs `JIRA_EMAIL`, `JIRA_API_TOKEN`, and `NTFY_TOPIC` also when the list leaves them out, and passes every secret to each session as an env var. An old `[secrets]` table, which mapped each name to a Bitwarden `item` and `field`, warns and is ignored.
Each host holds one machine token, `BWS_ACCESS_TOKEN=<token>` in `~/.config/bws/token.env` with mode 600, and no other copy of a secret. The run unit and the watch unit load that file and start the loop under `bws run` (Host), in [`secrets.ts`](../../loop/src/secrets.ts). `bws run` keeps the token from the loop. The run refuses an env that lacks a secret it needs. A changed secret needs no copy step: the next run gets it, and the watch page gets it when its service restarts.

### Hosts

Settles which machines can run the loop and what each needs. The loop runs on Linux with systemd and Node 22.18 or later, and the user has linger on (`loginctl enable-linger`), so the units outlive the login. `install.sh` installs the loop's packages with `npm ci` and links `~/.local/bin/loop` to `loop/bin/loop`, so a pull updates the command. `tools` lists the commands the repo needs beyond the script's own.

### Limits

Settles the numbers in rules 5 and 8. `[limits]` gives `parallel`, `agent_timeout_minutes`, `fix_attempts`, and `circuit_breaker`. The defaults are 1, 90, 2, and 2.

### Queue

Settles which tickets the dispatcher builds, in what order, and how often it looks. `[queue]` gives `filter`, the JQL of the queue in the order the tickets start, and `poll_minutes`, the minutes between two reads, default 2. The default `filter` is `component = "<component>" AND status in ("To Do", "<in_progress>", "<landed>") AND Flagged is EMPTY ORDER BY priority DESC, key ASC`, with the statuses of `[tracker]`, so a ticket that a worker left in progress or in review comes back. A wider filter is safe: the dispatcher still starts only a ready ticket (rule 1).

### Logs

The worktrees, the run folders, and the logs go to `~/.local/state/<name>-loop/`. A worker's folder is `tickets/<KEY>/` (The unit of work), and the dispatcher writes its own `decisions.jsonl` at the top of the state folder, with `dispatch` as its run name: a `queue` line when the queue's states change, a `worker` line when it starts a worker and when one ends, and its `hold`, `circuit-breaker`, `archive`, and `complete` lines. An old `<KEY>/` run folder is not read; the owner deletes it. The `name` in `loop.toml` also names the units and prefixes the Compose projects.
`loop watch`, in [`watch.ts`](../../loop/src/watch.ts), serves a page of these logs, and changes nothing the loop reads. One page serves every project on the host: each `<name>-loop` folder next to the state folder is a project, and each API path takes `?project=<name>`. The bare address opens the home page, from `/api/home`: the 5-hour window's use and reset time as one header line, a card for each project, and one log. The server works out each card from the project's current run, the running one or else the newest, so an older blocked or stopped run shows only in the Epic picker: needs you when the run has a needs-KC row, with each row; running while it runs or is paused, with each running ticket's step and since when, and the Epic's tickets complete of the total; else idle, with the run's Epic, status, and the time of its last line, or no runs yet. A card opens its current run. The log, from `/api/log`, is the latest 50 lines of every run of every project, newest first, or of one project with `?project=<name>`, without the `meter`, `tracker-status`, `frontier`, `notify`, and `agent` lines. Each gives its time, project, Epic, ticket, step, result, detail, and pull request, and a line with a ticket opens its detail. Inside a run, one menu button holds the Overview, Tickets, Diagnostics, and Usage views and the Epic picker. An address from before projects, `#/<Epic>/<view>`, opens that run and view of this repo's project. The page copies the start page's tokens, fonts, and card, dot, track, and issue shapes, with the run blue as its brand. A run's header gives its status: running, when the start line's `pid` is alive and no `stop` or `finish` line follows; paused, while a running run waits for a usage limit to reset; completed, when the run finished and every ticket merged or is done; blocked, when it finished with tickets left; failed, when the loop itself failed; stopped, also when the run has no end line because it was killed; or idle. The overview opens with what needs KC, worked out by the server in this order: a run whose process is gone with no end line, a pull request held by the hold label, a stuck ticket, checks that timed out, and a pull request that did not merge, each with the reason its line logged and a link to its pull request, or to the ticket when it has none. A row leaves once a later line clears it. Below that, it gives the tickets merged of the total, the plan meter of each window with its reset time, and the work queue: each running ticket with its step, how long it has run, and its health. A ticket needs attention when its agent has written nothing for `STALL_MINUTES`, 15, or its last checks are red, and is blocked while it waits for the usage limit. Each ticket shows its pull request and the state of its checks, from the `pr` and `wait` lines: Held for a held one, each check's name a link to its run, and why auto-merge is off when an `auto-merge` line follows the latest `pr` line. The Tickets view lists every ticket, and a ticket opens its detail: its blockers, its steps, and each session as one line per tool call, with each call that auto mode denied in red. The Diagnostics view gives the same for the whole run, with a failed `retarget` or `worktree` line as a warning. The Usage view opens with the meter and one line: this run's share of the 5-hour window per merged ticket, and the typical share, the median of the project's last 5 earlier runs that have one. A run with none is skipped, and with no earlier figure the line says there is no typical share yet. The server marks the line warn when this run's share is above 1.5 times the typical share, and the page draws it in the warn colour. One closed More fold holds this run's share of each window, what it delivered, and its cost against the run before. The page and its JSON API, such as `/api/home`, `/api/log`, `/api/epic/<run>`, `/api/agent/<run>/<KEY>/<n>`, `/api/usage`, `/api/report/<KEY>`, and `/api/forecast`, serve a person and an agent alike, and answer GET only. The page has no Start or Stop button: a run starts and stops with `loop start` and `loop stop`. It masks the value of each secret that `bws run` gave it, which it reads from its env: each one that the host's machine token reads, as `bws secret list` names them, so also a secret that only another project names. The page polls every 3 seconds and redraws what changed. It listens on localhost and on the host's tailnet address, at port 8790, `WATCH_PORT` in [`watch.ts`](../../loop/src/watch.ts). It answers only a request whose Host is localhost, the tailnet address, or the MagicDNS name, in full or as the host name alone, and gives 403 to any other, because a site whose name resolves to the host (DNS rebinding) sends its own name. It has no auth and no Origin check.
`loop report [<KEY>]`, in [`report.ts`](../../loop/src/report.ts), breaks down what the latest run of the key cost, or the latest run on the host. The cost that counts is the plan meter: the share of each window the run used, in percent, and that share per merged ticket. For each window, which one reset time names, the run used the highest `end` less the lowest `start` of its agent lines. The report then gives the tickets merged and stuck, the red checks, the head agent's turns, peak context, and hand-offs to each subagent tier per ticket, and the dollar figures, labelled `list price (API)`, because they are what the API would bill and not what the plan costs: by model, by subagent, and the Haiku cost above its 100K-token prompt rate. It compares each figure with the run before it on this host, or with the latest run of `--against <KEY>`, and `--json` prints the same as JSON.
The More fold of the Usage view ends with a capacity forecast, in [`forecast.ts`](../../loop/src/forecast.ts), which reads data only while More is open. It is for planning only. No run reads it, no agent sees it, and it never writes to Jira. When the page asks, `loop watch` reads the open Epics of each Jira project with a run on the host, with their tickets' keys and statuses, and keeps the read, or the error of a failed one, for `BACKLOG_MINUTES`, 5 minutes. `[watch]` `plans` lists the Claude plan from each time on, such as `{ plan = "max-5x", since = 2026-10-14T16:30:00Z }`; the plans are `pro`, `max-5x`, and `max-20x`, and `PLANS` holds Anthropic's multiple and monthly price for each. Open work gives one row per open Epic, with its tickets left and the share of a 5-hour and a weekly window they need. A ticket is left when Jira has it open, not in the landed status, and no run on the host merged it. Capacity gives the tickets that fit in a 5-hour window and in a week at the current plan's share per merged ticket, the weeks the open work needs, and the same for each bigger plan, scaled by its multiple, with its extra monthly price. Plans compared sets the plans side by side: the runs, the tickets merged, the share merged on the first checks, the fix attempts per merged ticket, the tickets stuck, the median time to merge less the waits for a usage limit, and the limits hit.
[`/check-loop`](../check-loop/SKILL.md) reads this design, the repo's settings, the run's logs, and the state of its pull requests, and tells KC in a few lines what is wrong, the proper fix, and whether it needs KC or an agent can make it.
