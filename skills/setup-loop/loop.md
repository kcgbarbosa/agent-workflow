# The loop

A script turns each ticket of an Epic into one pull request. It reads the ticket graph from the tracker, starts an agent for each ticket on the frontier, pushes the work, opens the pull request with auto-merge on, and waits for the shared merge gate on GitHub. A red gate goes back to the agent. No model decides what runs next or whether a ticket passed: the gate decides, and GitHub merges. The loop runs no gate, no code review, no UI review, no landing, no Epic branch, and no Epic pull request of its own.

This file is the one home of the fixed design. The `loop` command, from `loop/` in the agent-workflow repo, is the script for every repo. A repo's `loop.toml` holds the values the script reads, and its `docs/agents/loop.md` links here and holds the rest of its settings.

## Fixed design

Every repo keeps these rules. Change a rule here, on purpose, and give the reason in the pull request.

1. **Input and frontier.** `loop start <KEY>` runs an Epic, the children of `parent = <KEY>`, or a single ticket, and `loop start --filter <JQL>` runs the tickets the filter finds. A ticket is merged when a pull request of its branch has merged on GitHub, also one that merged before this run. A ticket is ready when it is open in the tracker, not flagged, and each of its blockers is done or merged, or when it has one blocker left whose pull request this run opened, which it stacks on (rule 2). A ticket with two open blockers waits, since a branch has one base. The tracker, GitHub, and the log (rule 11) hold all state.
2. **Worktree and branch.** Each ticket gets a worktree in the run's state folder and the branch `feat/<KEY>-<slug>`, or `fix/` for a Bug, from `origin/<main_branch>`. A branch of the key that is already on the host or on origin is used again. A ticket whose blocker has an open pull request stacks on it: its branch starts from that branch, and its pull request targets it. The ticket file, `ticket.md` in the ticket's run folder, holds the ticket text, the comments on the ticket, oldest first, and a Loop section: the Epic, the branch and the commit scope, the base it stacks on, the run folder, that the loop pushes and opens the pull request so the agent does neither, and that the gate runs every check so the agent runs the tests that cover its change. `agent_hint` adds a line to it.
3. **Agent run.** The script runs each session through the Claude Agent SDK, in [`agent.ts`](../../loop/src/agent.ts), with `/implement` and the ticket file as the prompt.
   - Every process the loop starts, the agent's Claude Code among them, starts through one function, `spawnGroup` in [`spawn.ts`](../../loop/src/spawn.ts), in a process group of its own, with `/dev/null` as stdin. At its limit, which is the agent timeout for a session, the script sends SIGTERM to the whole group, then SIGKILL to what still runs a minute later. The page opener of rule 12 does not, because the script does not wait for it.
   - No session gets background tasks (`CLAUDE_CODE_DISABLE_BACKGROUND_TASKS`), and the settings deny the tools that wait for a later turn, such as `ScheduleWakeup`, `CronCreate`, and `Monitor`. A session ends at its status, and nothing wakes it later.
   - The permission mode is `auto`, and the auto mode classifier learns that an unattended loop runs the session and owns each worktree under the state folder. Nobody answers a prompt, so a routine action that auto mode denies can block a ticket.
   - The system prompt is Claude Code's own, with [`dispatch.md`](../../loop/src/dispatch.md) added: the rule for when to hand work to the subagent tiers that `install.sh` links from [`agents/`](../../agents) to `~/.claude/agents`. `worktree.baseRef` is `head`, so a `trial` worktree branches from the ticket's last commit.
   - The model and effort are those of `[agent]` (Agent), so no session takes them from the host's own Claude Code settings.
   - Each session gets the host's environment without `BW_SESSION`, every secret of `[secrets]`, `LOOP_RUN_DIR` set to the run folder, and the env of its stack slot (Stack per worktree).
   - Each SDK message goes to `agent-<n>.jsonl` in the run folder as it comes, and the stderr of Claude Code to `agent-<n>.err`, so a run can be followed while it lasts.
   - The output schema returns `status` (`done` or `blocked`), `reason`, `decisions`, and `notes`. `decisions` holds only an open question that the ticket and the docs do not answer and that only KC can settle, and it is usually empty. The script takes the status from the result message. A session that returns no status, fails, or runs past its limit fails the build.
   - A fix attempt and a session that goes on after a usage limit resume the same session.
4. **Push and pull request.** After a `done` build with a new commit, the script pushes the branch. On the first push it opens the pull request, or takes the open one of the branch: the title `feat(<KEY>): <summary>`, or `fix(`, which becomes the squash commit on main, and a body that the gate's review reads the work against: a first line that links the ticket and names the spec, `Spec: [<path>](<link>)`, from the first Markdown file the Epic's description links, or `Spec: <path>` from a line of the ticket that names one, or no spec; then the agent's `reason`; then the ticket text under `## Ticket`. The agent's `decisions` go on the `pr` log line, not in the body, where a list of decisions reads as a list of blockers. It turns on auto-merge as a squash when the pull request targets `main_branch`. A stacked pull request gets auto-merge once it targets `main_branch` (rule 6). The ticket then goes to the review status (Status and stuck marker).
5. **Wait and fix.** The script polls the checks of the pull request with `gh` every 30 seconds, `LOOP_POLL_SECONDS`, for up to `WAIT_MINUTES` in [`run.ts`](../../loop/src/run.ts), 120. A check counts once the pull request's head is the pushed commit. A merged pull request is green. A failed or cancelled check is red, except `hold`, `HOLD_CHECK`: it fails while the pull request has the hold label (Gate), which is a pause and not a red gate, so the script logs one `wait` `held` line and waits for the label to go, and the wait's limit does not run while it stays. With auto-merge off, every check passing or skipped is green. A red gate resumes the session as a fix attempt, with one message: the end of each failed job's log, the last `LOG_TAIL_LINES` (80), and the blocking findings of the gate's review. The fix commits, the script pushes, and the gate runs again. A fix that makes no new commit counts as an attempt. After `fix_attempts` fix attempts the gate is still red, the ticket is stuck. A closed pull request and a wait past its limit stop the ticket.
6. **Merge and stack.** GitHub merges a green pull request with auto-merge on. When auto-merge is off, the script merges it. After each merge, each open pull request that targets the merged branch targets `main_branch`, because GitHub retargets it when the branch is deleted, and the script retargets it itself when GitHub did not. A stacked ticket whose gate is green waits until its pull request targets `main_branch`, then turns on auto-merge. When its blocker stops instead, it stops too.
7. **Stuck.** The script comments `The loop stopped this ticket.` on the ticket, with the reason, the pull request, and the log path on the host, sets the Jira Flagged field, and notifies. A comment that is already on the ticket is not posted again. Other frontier tickets keep running. Tickets downstream of a stuck one wait. KC gives a stuck ticket a new start by removing its flag.
8. **Limits.** `parallel` tickets build at once, each in its own worktree and stack slot. A run of stuck tickets in a row as long as `circuit_breaker` stops new tickets from starting. A usage limit that resets within `MAX_USAGE_WAIT_SECONDS` in [`run.ts`](../../loop/src/run.ts), 6 hours, pauses the run: the script notifies once, waits until a minute after the reset that the session's `rate_limit_event` gives, and resumes each session that met the limit. A limit with no reset time, or a later one, stops the run and notifies.
9. **Restart.** A ticket is a fixed list of steps: build, push, pull request, wait, merge. A run or a restart starts each ticket at its first step with no pass at the branch's HEAD. A ticket whose pull request merged before the run is merged, and is not built again. A ticket with an earlier start line starts as a restart, on the same worktree and branch, and resumes its session. The script counts the fix attempts from the log, since the ticket was last stuck, so a fix that a kill stops still uses its attempt. A push, a `gh` call, and a Jira call change nothing when they run again, so a step that runs again repeats no side effect. A kill between a merge and its retarget is finished at the next start.
10. **Finish and Epic complete.** When no ticket is left to start and nothing runs, the script logs a `finish` line with the merged tickets, the stopped ones, the ones that wait on a blocker, and the limit that stopped the run, and notifies. Before it, when the run has an Epic, the Epic is open, and every ticket of the Epic has merged or is done, the script archives the spec, in [`archive.ts`](../../loop/src/archive.ts), then moves the Epic to `Done`, `EPIC_DONE` in [`run.ts`](../../loop/src/run.ts). The run of the Epic's last ticket alone archives it too. Each link of the Epic description of the form `<repo>/blob/<ref>/<path>.md`, where `<repo>` is the repo of the merged pull requests and `<ref>` is not a commit SHA, changes to link the head of `origin/<main_branch>`, in its text and its target, so git keeps the spec. When a linked path is still on `origin/<main_branch>`, the script deletes the paths on the branch `docs/<Epic key>-archive-spec`, in a worktree of `origin/<main_branch>` in the run's state folder, pushes it, opens a pull request with the title `docs: archive the spec of <Epic summary>` and the pinned links in its body, and turns on auto-merge. The title has no key, so its merge moves nothing in Jira. An open pull request of that branch is used again. The log gets an `archive` line with the result `pr-open`, `archived` when no path is left on main, `no-spec` when the description links no spec of the repo, or `fail`, then a `complete` line, and the script notifies. The Epic does not wait for the archive pull request, which merges on its own once its gate is green: the `complete` line names it while it is open. A failed archive leaves the Epic open, so the next run tries again. A run that finds the Epic done archives nothing.
11. **Log.** One JSONL line per step in `decisions.jsonl`, with `time`, `epic` (the run's name: the key, or `filter-<hash>` for a filter), `ticket`, `step`, `result`, `commit`, `session`, and `detail`, in [`log.ts`](../../loop/src/log.ts). The steps are `start`, `frontier`, `build` (`started`, then `pass`, `fail`, or `blocked`), `agent`, `push`, `pr`, `wait`, `base`, `merge`, `retarget`, `stuck`, `tracker-status`, `slot`, `meter`, `usage-pause`, `circuit-breaker`, `archive`, `complete`, `notify`, `stop`, and `finish`. The run's `start` line adds `input`, the `pid`, and `setup`: the `claude` version, and the model and effort of the head agent, of each subagent tier, and of the gate's review, so two runs can be told apart. The `frontier` line adds `summary` and `tickets`, each with its key, summary, status, state, and blockers. A ticket's `start` line adds `slot`, and `base` and `pr` when it stacks. A `build` `started` line adds `attempt`. The `pr` line adds `pr` and `auto_merge`, and `decisions` when the agent returned any, and the `wait` line (`held`, then `green`, `red`, or `timeout`) adds `checks`, each with its `name` and `bucket`, so the watch page shows each pull request and its checks with no call to GitHub. Each `agent` line adds `usage`, from the session's result message: `total_cost_usd`, `num_turns`, `duration_ms`, the subagents by type, the usage of each model, and `peak_context`, the largest context that one of the session's own assistant messages sent. A resumed session reports its whole cost so far, so the last agent line of a session holds its total. Each agent line adds `plan`, the Claude plan meter over the session from its `rate_limit_event` messages: for each of `five_hour` and `seven_day`, the first and the last utilization as `start` and `end`, and `resets_at`. While a session runs, the script logs a `meter` line with the newest reading of each window when it changed, at most once a minute, `LOOP_METER_SECONDS`. The meter belongs to the account, so parallel runs and KC's own sessions move it together, and `loop report` counts it per run. Each reader skips a line that does not parse.
12. **Host.** Each run is a systemd user unit, so systemd knows whether it is alive, and the run outlives the agent or shell that starts it. [`units.ts`](../../loop/src/units.ts) holds the unit settings.
    - `loop start` first fast-forwards the loop's own checkout of agent-workflow to `origin/main`, so every host runs the merged loop, and refuses with git's message when a change that is not committed overlaps the new commits. A checkout on another branch runs as it is. It then reads only `name` from `loop.toml`, with no check of the other keys, so a key that only the new code knows reaches the new code. It refuses when the host has no secrets file, or when a run of the repo is active, and names that run's unit.
    - It starts `loop run` as the transient unit `loop-<name>-<run>`, with `systemd-run --user --collect --service-type=exec`, `KillMode=mixed`, and `TimeoutStopSec=10min`, and returns when the unit runs. The unit gets `PATH`, `HOME`, `LANG`, and `SSH_AUTH_SOCK` from the shell that starts it, because the user manager's own environment differs between a desktop login and a boot with linger. `--collect` unloads the unit when the run ends, also when it fails, so a failed run never blocks the next start. The unit's journal, `journalctl --user -u loop-<name>-<run>`, holds the run's output.
    - It then starts `loop watch` (Logs) as the user service `loop-watch-8790` when it is not active, and restarts the service when it took new commits. The service restarts after a crash. One page serves every project on the host. On a host with a screen, it opens the page, and it prints the page's tailnet address, which opens on any device in the tailnet.
    - The run refuses to start when `git`, `gh`, `claude`, `systemd-inhibit`, a command of `tools`, or `docker` for a repo with a stack is not on the PATH, or when the secrets file lacks a secret. It holds off sleep with `systemd-inhibit`, which runs beside it: systemd sends the SIGTERM of a stop to the unit's main process only, so the run must be that process.
    - `loop stop <KEY>`, or `loop stop --filter <JQL>`, stops the unit, and returns when the run has ended. The run takes the SIGTERM as a stop: it logs `stopped`, ends every agent session through the process function (rule 3), and notifies. The step in progress writes no result, and no `finish` line follows. Systemd kills what still runs after 10 minutes. The next `loop start` goes on with the same tickets (rule 9).
    - An agent starts a run only with `loop start`, because the Bash tool stops a command after 10 minutes.
13. **Main.** The loop never writes to `main_branch`. Work reaches it only through a pull request that the gate passed, and a merge to main is not a release.

## Settings

Each section names what it settles, and its `loop.toml` key when the script reads one. A repo's `docs/agents/loop.md` keeps these headings. A value with a key lives in `loop.toml` only, and the repo doc points there; the doc holds the values the script cannot read. A key that the old loop read and this one dropped, `[gates]`, `[acceptance]`, `[ui]` `skill`, and `[demo]`, prints a warning that names it and is ignored. Any other unknown key refuses the file.

The machine README, `~/.local/share/chezmoi/README.md`, holds how to reach each machine and how secrets get onto it. Secrets and Hosts link to it.

### Run

Settles who starts a run, and where. The command is `loop start <KEY>` or `loop start --filter <JQL>` in the main checkout, and `loop stop` stops it (rule 12). One run of a repo goes at a time on a host, because every run uses the same stack slots. Each host knows only its own units, so two hosts can both start a run on the same Epic. A person keeps it to one run at a time across hosts.

### Tracker

Settles the tracker and how the Epic's children and blocking edges are stored. `[tracker]` gives `kind` and `url`. Jira is the only adapter. It reads the children of an Epic as the issues with `parent = <Epic key>`, and a blocking edge as a "Blocks" issue link. It signs in with basic auth, the account email and an API token without scopes, on the site URL. It marks a stuck ticket with the Jira Flagged field, so the site needs that field. `name_landed_keys_only` is still read and checked, and the loop uses it for nothing, because the loop opens no Epic pull request.

### Status and stuck marker

Settles which status changes the loop makes, which the tracker's automation makes, and how a stuck ticket shows. `tracker.in_progress` is the status of a ticket that starts, and `tracker.landed` the status of a ticket whose pull request opens. Each must match a status name of the workflow exactly, and the workflow must offer a transition to it from the status that a ticket has at that point. The tracker's automation sets a ticket's done status when its pull request merges. The loop sets `Done` on the Epic only, at its last merge (rule 10).

### Human steps

Settles what only a person can do, and how tickets carry it.

### Branches and commits

Settles where the key goes in commits. The script names each branch `feat/<KEY>-<slug>`, or `fix/` for a Bug, and each pull request title `feat(<KEY>): <summary>`, which the squash merge makes the commit on main. `main_branch` names the branch each pull request targets, unless it stacks.

### Gate

Settles the checks that decide a pull request. The shared merge gate, `.github/workflows/gate.yml` in agent-workflow, runs the repo's `make check`, then `gate / review` and `gate / judge`; `setup-repo` puts a repo on it. `agent_hint` adds a line to each ticket file for what the gate does not say, such as what the tests need from the stack. The `[review]` table, with `enabled`, `model`, `effort`, and `skip`, and `[ui]` `blocking` are settings of the gate, which `actions/review/action.yml` and `actions/judge/action.yml` read. The script checks their types, logs the review's model and effort in `setup`, and uses none of them. The `hold` label on a pull request makes the required `hold` check fail, so GitHub keeps a green pull request from merging until the label goes, and the script waits with it (rule 5).

### Stack per worktree

Settles how two tickets run full stacks side by side. `[stack]` gives the base `ports` and the `port_step` per slot. A repo with no stack leaves it out.
Slot 0 is the main checkout, so a person's own stack keeps the base ports, and slot 1 stays free, so the tickets in flight use slot 2 and up. For each key under `ports`, the script sets an env var of that name to the slot's port, and sets `COMPOSE_PROJECT_NAME` to `<name>-<key>`, and the repo's Compose files and dev server configs read them. The agent starts and stops its own stack. Before each session, the script reads `docker ps` for the containers of other Compose projects, such as a stack from a session outside the loop. When one holds a port of the slot, the slot moves to the first free one of `SPARE_SLOTS` in [`run.ts`](../../loop/src/run.ts), 8, after the ticket slots, for the rest of the run, and the script logs a `slot` line with the container. With no spare slot free, the ticket is stuck, and the reason names the container.

### UI review

Settles the UI paths and what the gate's judge checks. `[ui]` gives `path`, one folder prefix of the UI, `accepted_unchecked`, phrases for the parts that a review is known not to check, and `blocking`, the faults that fail `gate / judge`. The script checks them and uses none of them. A repo with no UI leaves it out.

### Agent

Settles what the head agent runs on. `[agent]` gives `model` and `effort`, and the defaults are `claude-opus-5-5` and `high`. Effort is the setting to change to cut cost: at every cost, Opus 5.5 scores at or above Sonnet 5.5. Each turn sends the whole context again, so the cost of a ticket grows with how large its sessions get, and `loop report` shows each session's peak context.

### Connectors

Settles which MCP servers the agent gets. The script passes no MCP configuration of its own. Each server adds its tool names and instructions to the context of every turn, and the ticket file already holds the ticket text, so a run needs no tracker connector.

### Notifications

Settles the channel, the events, and what a message may contain. `notify.url` is the ntfy server, and the `NTFY_TOPIC` secret is the topic. The events are a stuck ticket, `<KEY> stuck`; a pause, `<run> paused`; a usage limit that stops the run, `<run> stopped at a usage limit`; a stop, or a failure of the loop itself, `<run> stopped`; an Epic complete, `<Epic key> complete`; and the finish, `<run> finished.` with what it merged and stopped. A message holds keys and statuses only. Anyone who knows the topic can read the messages, so the topic is a secret.

### Secrets

Settles which secrets the loop needs and where each one lives. `[secrets]` maps each env var to its Bitwarden `item` and `field`. The script needs `JIRA_EMAIL`, `JIRA_API_TOKEN`, and `NTFY_TOPIC`, and passes every secret to each session as an env var.
`loop secrets`, in [`secrets.ts`](../../loop/src/secrets.ts), copies them from an unlocked Bitwarden to `~/.local/state/<name>-loop/secrets.json`, with mode 600. It refuses a locked vault, and writes no file when the vault lacks one of them. Run it once per host, and again after a secret changes. The file is the only place a run reads secrets from, so a run never needs an unlock.

### Hosts

Settles which machines can run the loop and what each needs. The loop runs on Linux with systemd and Node 22.18 or later, and the user has linger on (`loginctl enable-linger`), so the units outlive the login. `install.sh` installs the loop's packages with `npm ci` and links `~/.local/bin/loop` to `loop/bin/loop`, so a pull updates the command. `tools` lists the commands the repo needs beyond the script's own.

### Limits

Settles the numbers in rules 5 and 8. `[limits]` gives `parallel`, `agent_timeout_minutes`, `fix_attempts`, and `circuit_breaker`. The defaults are 1, 90, 2, and 2.

### Logs

The worktrees, the run folders, and the logs go to `~/.local/state/<name>-loop/<run>/`, where the run is the key or `filter-<hash>`. The `name` in `loop.toml` also names the run units and prefixes the Compose projects.
`loop watch`, in [`watch.ts`](../../loop/src/watch.ts), serves a page of these logs, and changes nothing the loop reads. One page serves every project on the host: each `<name>-loop` folder next to the state folder is a project, and each API path takes `?project=<name>`. The bare address opens the home page, from `/api/home`, with the plan meter and a panel for each project that lists its latest runs. A run's header gives its status: running, when the start line's `pid` is alive and no `stop` or `finish` line follows; paused, while a running run waits for a usage limit to reset; completed, when the run finished and every ticket merged or is done; blocked, when it finished with tickets left; failed, when the loop itself failed; stopped, also when the run has no end line because it was killed; or idle. The overview gives the tickets merged of the total, the plan meter of each window with its reset time, and the work queue: each running ticket with its step, how long it has run, and its health. A ticket needs attention when its agent has written nothing for `STALL_MINUTES`, 15, or its last checks are red, and is blocked while it waits for the usage limit. Each ticket shows its pull request and the state of its checks, from the `pr` and `wait` lines. The Tickets view lists every ticket, and a ticket opens its detail: its blockers, its steps, and each session as one line per tool call, with each call that auto mode denied in red. The Diagnostics view gives the same for the whole run. The Usage view gives the meter, this run's share of each window, and its cost against the run before. The page and its JSON API, such as `/api/epic/<run>`, `/api/agent/<run>/<KEY>/<n>`, `/api/usage`, `/api/report/<KEY>`, and `/api/forecast`, serve a person and an agent alike, and answer GET only. The page has no Start or Stop button: a run starts and stops with `loop start` and `loop stop`. It masks the value of each secret in every project's secrets file. The page polls every 3 seconds and redraws what changed. It listens on localhost and on the host's tailnet address, at port 8790, `WATCH_PORT` in [`watch.ts`](../../loop/src/watch.ts). It answers only a request whose Host is localhost, the tailnet address, or the MagicDNS name, in full or as the host name alone, and gives 403 to any other, because a site whose name resolves to the host (DNS rebinding) sends its own name. It has no auth and no Origin check.
`loop report [<KEY>]`, in [`report.ts`](../../loop/src/report.ts), breaks down what the latest run of the key cost, or the latest run on the host. The cost that counts is the plan meter: the share of each window the run used, in percent, and that share per merged ticket. For each window, which one reset time names, the run used the highest `end` less the lowest `start` of its agent lines. The report then gives the tickets merged and stuck, the red checks, the head agent's turns, peak context, and hand-offs to each subagent tier per ticket, and the dollar figures, labelled `list price (API)`, because they are what the API would bill and not what the plan costs: by model, by subagent, and the Haiku cost above its 100K-token prompt rate. It compares each figure with the run before it on this host, or with the latest run of `--against <KEY>`, and `--json` prints the same as JSON.
The Usage view ends with a capacity forecast, in [`forecast.ts`](../../loop/src/forecast.ts), a closed panel that reads data only while it is open. It is for planning only. No run reads it, no agent sees it, and it never writes to Jira. When the page asks, `loop watch` reads the open Epics of each Jira project with a run on the host, with their tickets' keys and statuses, and keeps the read, or the error of a failed one, for `BACKLOG_MINUTES`, 5 minutes. `[watch]` `plans` lists the Claude plan from each time on, such as `{ plan = "max-5x", since = 2026-10-14T16:30:00Z }`; the plans are `pro`, `max-5x`, and `max-20x`, and `PLANS` holds Anthropic's multiple and monthly price for each. Open work gives one row per open Epic, with its tickets left and the share of a 5-hour and a weekly window they need. A ticket is left when Jira has it open, not in the landed status, and no run on the host merged it. Capacity gives the tickets that fit in a 5-hour window and in a week at the current plan's share per merged ticket, the weeks the open work needs, and the same for each bigger plan, scaled by its multiple, with its extra monthly price. Plans compared sets the plans side by side: the runs, the tickets merged, the share merged on the first checks, the fix attempts per merged ticket, the tickets stuck, the median time to merge less the waits for a usage limit, and the limits hit.
[`/check-loop`](../check-loop/SKILL.md) reads this design, the repo's settings, the run's logs, and the state of its pull requests, and tells KC in a few lines what is wrong, the proper fix, and whether it needs KC or an agent can make it.
