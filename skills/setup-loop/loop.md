# The loop

A script builds one Epic unattended. It reads the ticket graph from the tracker, starts an agent for each ticket on the frontier, runs the gates itself, and lands each green ticket on the Epic branch. No model decides what runs next or whether a ticket passed. KC merges the Epic PR into `main`.

This file is the one home of the fixed design. The `loop` command, from `loop/` in the agent-workflow repo, is the script for every repo. A repo's `loop.toml` holds the values the script reads, and its `docs/agents/loop.md` links here and holds the rest of its settings.

## Fixed design

Every repo keeps these rules. Change a rule here, on purpose, and give the reason in the pull request.

1. **Frontier.** A ticket is on the frontier when it is open, not stuck, and each of its blockers is done in the tracker or landed on the Epic branch. A ticket has landed when `git log <epic-branch> --grep "(<KEY>)"` finds its merge. The tracker, git, and the log (rule 11) hold all state. A ticket that is done in the tracker but whose branch holds work on neither main nor the Epic branch is not built. The script notifies at start and marks it in the Epic PR.
2. **Worktree.** Each ticket gets a worktree and a branch off the Epic branch, its own stack, and a ticket file outside the repo. The ticket file holds the ticket text and names the gate command that the script runs on the work after the agent returns `done`: the ticket gate. It also names the merge gate, which runs every test at landing, and tells the agent to run the tests that cover its change, so the agent does not run either gate first. It also holds the comments on the ticket, without the loop's own stuck and decisions comments, which the script knows by their first line. When the comments cannot be read, the script logs it and writes the ticket file without them. When a remote branch already carries the key, the script uses that branch, and the ticket starts as a restart (rule 9). The script pushes the ticket branch after every agent run. Claude Code makes the worktree of a `trial` subagent under `.claude/worktrees/` in the main checkout, and removes it when the trial leaves no change. Each time the integrator takes the ticket from its worker (rule 8), it also removes the trial worktrees that the ticket's runs left, with their branches: each one that is not locked and whose commit is on the ticket branch but not on main.
3. **Agent run.** For a ticket, the script runs `claude -p` with `/implement` and the ticket file as the prompt. [`EpicRun.agent_command`](../../loop/src/loop/run.py) holds the whole command, and every agent run, for a ticket or for the finish, gets these parts:
   - Each command that the script waits for, such as an agent run, a gate, the demo command, or a `git`, `gh` or `docker` call, starts through one function, [`process.run`](../../loop/src/loop/process.py). The sleep inhibitor and the page opener of rule 12 do not, because the script does not wait for them. The command gets a session of its own and `/dev/null` as stdin, so it has no controlling terminal, and no terminal can stop it. At its limit, which is the agent timeout for an agent run, the script sends SIGTERM to the command's whole process group, then SIGKILL to what still runs a minute later. For an agent run or a gate, it then stops the stack of that worktree with `docker compose down`, because containers run under dockerd and outlive the group.
   - No agent run gets background tasks (`CLAUDE_CODE_DISABLE_BACKGROUND_TASKS`), so each Agent and Bash call runs in the foreground. A session ends at its status, and a background task or subagent would end unread or wake the session too late. The settings deny the tools that wait for a later turn, such as `ScheduleWakeup`, `CronCreate`, and `Monitor`, and `BASH_MAX_TIMEOUT_MS` lets one Bash call run as long as the gate timeout, so a long command, such as the acceptance tests, fits in the foreground. The head agent's system prompt tells it that its status ends the session. A session that still runs 10 seconds after its status is stopped in the same way, with its stack, because the status is its last word. A review's prompt tells it to stop each server it started before it returns its result.
   - `--permission-mode auto` and `--permission-prompts none` let the run go on with nobody there to answer a prompt.
   - `--output-format stream-json` with `--verbose` writes each event to the agent log as it happens, so a run can be followed while it lasts.
   - `--json-schema` makes the run return its status in a fixed shape.
   - `-n` names the session after the ticket key.
   - `--mcp-config` gives the run the worktree's `.mcp.json` when it has one, because nobody approved the project's MCP servers in a new worktree folder. `--strict-mcp-config` then gives the run only those servers (Connectors).
   - Every run gets the loop's subagent tiers from `~/.claude/agents`, where `install.sh` links the files in [`agents/`](../../agents). [`tiers.py`](../../loop/src/loop/tiers.py) reads the same files only for the start line (rule 11). `--append-system-prompt` adds the rule for when to hand work to them in [`dispatch.md`](../../loop/src/loop/dispatch.md). A run of `implement` outside the loop gets the tiers, and not the rule.
   - `--settings` gives the rules of [`agent_settings`](../../loop/src/loop/claude.py): the gate commands run without the classifier, and the classifier learns that the `<name>-<key>` stacks are the loop's own, so an agent can stop one to free a port. `worktree.baseRef` is `head`, so a `trial` worktree branches from the ticket's last commit rather than from main. No agent run deletes a volume. Nobody answers a prompt in a run, so a routine action that auto mode denies makes a ticket stuck.
   - `--resume` continues the session for a fix attempt.
   - `--autocompact` sets the window that every run compacts at, `CONTEXT_TOKENS` in [`config.py`](../../loop/src/loop/config.py) (Agent).
   - `--model` and `--effort` run the review sessions of rules 4 and 5 on `REVIEW_MODEL` at `REVIEW_EFFORT` in [`claude.py`](../../loop/src/loop/claude.py). Every other run, the head agent's sessions and the PR body, runs on the model and effort of `[agent]` (Agent), so no run takes them from the host's own Claude Code settings.

   The schema returns `status` (`done` or `blocked`), `reason`, `decisions`, and `notes`. `decisions` holds only an open question that the ticket and the docs do not answer and that only KC can settle, and it is usually empty. `notes` holds everything else worth keeping, such as a judgement call that follows the docs. The script comments both on the ticket. Neither goes in the Epic PR, because a ready PR means the loop verified everything, and a list of decisions in it reads as a list of blockers. Each turn ends with a result event, and the script takes the status from the last result event that has one. A `blocked` status makes the ticket stuck.

4. **Ticket gate and code review.** The script runs the ticket gate in the worktree. When it fails, the script resumes the session with the tail of the log, up to the fix attempt limit. When it passes and the repo has `[acceptance]` (Acceptance tests), the script lists the ticket's acceptance tests and compares their titles with the lines of what the user sees. A line with no test of the same name fails the ticket gate, and the script resumes the session with the missing lines, as a fix attempt. Still failing, the ticket is stuck. Every gate starts as the agent does (rule 3), with the gate timeout as its limit, so a gate past its limit fails, and its processes and its stack stop with it. A short command, such as `gh` or `docker compose down`, also has the gate timeout as its limit. When the gate passes, the script runs `/code-review` against the Epic branch in a new session. Its prompt names both gates, so the review reads the diff and its tests, and runs a test only to confirm a problem that it suspects. The review returns the findings that need a change, which are the breaks of the behaviour, the ticket, or a documented standard, and it lists polish that blocks nothing in `notes`, after every subagent it started has returned, as its result ends the session. The script resumes the head agent's session to fix them, and the ticket gate runs again. A commit after a code review gets a new review. A later review looks only at the ticket's own commits since the commit of the last review, and gets that review's findings, numbered. It returns in `open` the number of each earlier finding that is still not fixed, so each round reviews less than the one before it, and a fix is not reviewed again as new code. A review with a finding in `open` sends a fix attempt. New findings in a fix are not a fix attempt, but a review that still finds problems after `MAX_REVIEW_ROUNDS` rounds in [`run.py`](../../loop/src/loop/run.py), 4, makes the ticket stuck, so two fixes that undo each other cannot keep a ticket running. Findings that the head agent answers with no commit pass, because the agent gives the reason for each one it keeps in `notes`. The ticket file tells the head agent that the loop runs the reviews.
5. **UI gate.** When the diff against the Epic branch touches a UI path, the script runs the UI review skill in a new session after the code review. The review saves its screenshots in the screenshot folder, `screenshots/` in the run folder (`SHOTS_DIR` in [`config.py`](../../loop/src/loop/config.py)), which its prompt names, and returns each fault it sees. The UI review only advises: a fault never goes back to the head agent and never sticks the ticket. The ticket lands, and the fault is open, because a UI fault costs less to fix by hand, or in one polish ticket, than to build and review again. An environment that lacks something a screen needs, such as a secret or a bucket, blocks the review, and a screen that shows an error in place of its content is a fault. A part that the seeded data cannot show, such as a list of three when the seed has one, goes in `unchecked`, with its path and the reason. An unchecked part whose text holds a phrase of `[ui]` `accepted_unchecked` is a note on the ticket. Any other unchecked part is open too. The script comments each open item on the ticket and logs the items with the result. The Epic PR lists each ticket whose last UI review left items open (rule 10). A review that is blocked, fails, or saves no screenshots is an open item too, and the ticket lands. A review that goes on after a usage limit keeps the screenshots it saved. A UI review passes for each later commit where the ticket's own change to the UI paths is the same as at the reviewed commit, so a later commit with no UI change, or a merge of the Epic branch, gets no new UI review. The script attaches the screenshots to the ticket, from the screenshot folder only, because an agent can save other images in the run folder, such as the screenshots of each acceptance run.
6. **Land.** Only the integrator (rule 8) lands, so merges run one at a time: `git merge --no-ff` into the Epic branch, with the key in the message, then the merge gate on the Epic branch. When the gate passes, the Epic branch takes the merge and the script pushes it. A failed push is logged, and the run goes on. A conflict or a failed merge gate undoes the merge. The script then merges the Epic branch into the ticket branch, removes the ticket's database volume so that the migrations the merge brought in run from the start, and resumes the session as a fix attempt, to resolve the conflict or to fix the cause from the tail of the gate log. Out of fix attempts, the ticket is stuck.
7. **Stuck.** The script sets the stuck marker on the ticket, comments the reason and the log path, and notifies. Other frontier tickets keep running. Tickets downstream of a stuck one wait.
8. **Limits.** Parallel tickets, the agent timeout, and fix attempts per ticket cap the work. Each ticket in flight has a worker, which takes it through the build, the gates, and the reviews in the ticket's own worktree, and never touches the Epic worktree or the main checkout. One thread, the integrator, does the rest that tickets share: it adds and removes the worktrees, lands (rule 6), and pauses. It takes the ticket from the worker after each build, at the landing, at a usage limit, and when the ticket is stuck, and gives it back to go on. The only locks are on the log appends and on the slot moves (Stack per worktree). A run of stuck tickets in a row as long as the circuit breaker stops the loop. A usage limit that resets within 6 hours pauses the session: the integrator notifies once, waits for the reset that the run's `rate_limit_event` gives, and gives back each ticket that met the limit, which resumes its session. Any other usage limit stops the loop and notifies.
9. **Restart.** A ticket is a fixed list of steps: build (a run of the head agent), ticket gate, code review, UI gate, and land. A run or a restart starts each ticket at its first step with no pass at the branch's HEAD, so a restart never runs work that is done. A new commit voids the passes after it, except the pass of the UI gate (rule 5). A step with a `started` line and no result runs again. A build that goes on after a usage limit is the same build, with no new `started` line, and a review that goes on after one writes its `started` line again. Review findings at HEAD that no run of the head agent answered go back to the agent with no new review. At the start, the script finishes each landing and each stuck step that a kill stopped. Each Jira call reads the ticket first, and a push or a `gh` call changes nothing when it runs again, so a step that runs again repeats no side effect. A restart is not a fix attempt. The script counts the fix attempts and the review rounds from the log, since the ticket was last stuck, so a fix that a kill stops still uses its attempt, and KC gives a stuck ticket a new start when KC removes its flag. The script keeps the branch of each ticket in progress. A run of the head agent in a new session, as on a restart, gets the prompt of a first build, with the fix when it has one.
10. **Finish.** When the frontier is empty and nothing runs, the script runs the merge gate on the Epic branch, pushes it, points the demo at it when the repo has one (Demo), and opens the Epic PR. It runs no review, because each ticket got its code review at landing (rule 4), and the review of the whole Epic is KC's. An agent writes the PR body with the `pr` skill, and names in Evidence each test that the merge gate log shows as flaky. Without a body from it, the body is the ticket table. If a gate or the demo command still fails, or a ticket is stuck, not built, or done in the tracker but not landed, the PR is a draft. The failing gate, the failed demo command, and the unfinished tickets go at the top of a draft, because a merge of the Epic PR can close the Epic and all of its children in the tracker. The tickets with open UI items follow them, on a ready PR too. Then it notifies.
11. **Log.** One JSONL line per decision, with the ticket, step, result, commit, and session id, in the log folder outside the repo. Each step of rule 9, and the stuck step, writes a `started` line and then its result with the commit at that time. The result of a failed gate is the line of its command. A review that sends back the findings of an earlier result writes no new result. A review result adds its `findings`, a code review result its `open`, an open UI review adds its `items`, the `started` line of a build adds `attempt` when the build is a fix attempt, and the `started` line of the stuck step adds its `comment`. The script ends a last line that a kill cut off, and each reader skips a line that does not parse. Each agent line adds `usage`, from the run's last result event: `total_cost_usd`, `num_turns`, `duration_ms`, the subagents by type, and the usage of each model. A resumed session reports the cost and the models of the whole session so far, so the last agent line of a session holds its total. `usage` also gives `peak_context`, the largest context that one of the session's own assistant messages sent: its input, cache read, and cache write tokens. Each agent line adds `plan`, the Claude plan meter over the run from its `rate_limit_event` lines: for each of `five_hour` and `seven_day`, the first and the last utilization as `start` and `end`, and `resets_at`. A run that meets a usage limit logs its agent line too, with the result `usage-limit`, and the pause adds `resumes`, the time the integrator goes on. While an agent runs, the script logs a `meter` line with the newest reading of each window, as `utilization` and `resets_at`, when the reading changed, at most once a minute. The meter belongs to the account, so parallel runs and KC's own sessions move it together, and `loop report` counts it per Epic run, not per ticket (Logs). The Epic's start line adds `setup`: the `claude` version, and the model and effort of the head agent, of each subagent tier, and of the reviews, so two runs can be told apart.
12. **Host.** Each run is a systemd user unit, so systemd knows whether it is alive, and the run outlives the agent or shell that starts it. [`units.py`](../../loop/src/loop/units.py) holds the unit settings.
    - `loop start` first fast-forwards the loop's own clean checkout of agent-workflow to origin, so every host runs the merged loop, and refuses when it cannot. It then reads only `name` from `loop.toml`, with no check of the other keys, so a key that only the new code knows reaches the new code. It refuses when the host has no secrets file, or when a run of the repo is active, and names that run's unit.
    - It starts `loop run` as the transient unit `loop-<name>-<Epic key>`, with `systemd-run --user --collect`, and returns when the unit is active. The unit gets `PATH`, `HOME`, `LANG`, and `SSH_AUTH_SOCK` from the shell that starts it, because the user manager's own environment differs between a desktop login and a boot with linger. `--collect` unloads the unit when the run ends, also when it fails, so a failed run never blocks the next start. The unit's journal, `journalctl --user -u loop-<name>-<Epic key>`, holds the run's output.
    - It then starts `loop watch` (Logs) as the user service `loop-watch-8790` when it is not active, and restarts the service when it took new commits. The service restarts after a crash. One dashboard serves every project on the host. It opens the page and prints its tailnet address, which opens on any device in the tailnet.
    - The run checks every other prerequisite before it starts, and refuses to run when one is missing. A check, such as `docker info`, that gives no answer in 2 minutes has failed. A `claude` older than `MIN_CLAUDE` in [`claude.py`](../../loop/src/loop/claude.py) counts as missing, because an older one does not know every model the tiers name, or does not end its background commands under `-p` and exit on SIGTERM. The run holds off sleep with `systemd-inhibit`, which runs beside it: systemd sends the SIGTERM of a stop to the unit's main process only, so the run must be that process.
    - `loop stop <Epic key>` stops the unit, and returns when the run has ended. The run takes the SIGTERM as a stop. No new agent run or gate starts. The step in progress ends its command through the process function (rule 3), with the stack of its worktree, and writes no result. The run then logs `stopped`, notifies, and stops every stack of the repo (Stack per worktree). A stop during the prerequisite checks, before the start line, ends the run with no `stopped` line, because nothing ran yet. A stop after the last gate of the finish lets the finish open the PR. Systemd kills what still runs after 10 minutes. The next `loop start` goes on with the same tickets (rule 9).
    - The dashboard's Start and Stop (Logs) call the same functions as `loop start` and `loop stop`. Start does not fast-forward the checkout, so the run gets the code that the dashboard runs.
    - An agent starts a run only with `loop start`, because the Bash tool stops a command after 10 minutes.
13. **Main.** The loop lands work only on the Epic branch. KC merges the Epic PR. KC can push to the Epic branch on origin between runs, such as a merge of `main` that resolves a conflict of the Epic PR. At the start and at the finish, the script merges `origin/<Epic branch>` into the Epic branch when it is not there yet, so the run builds on those commits and its push is not refused. A merge that conflicts is aborted and stops the run.
14. **Stacked Epic.** `loop start <Epic key> --on <branch>` builds the Epic on a branch of origin that is not merged yet, such as the branch of the previous Epic's PR, so the next Epic can run while KC has not reviewed the last. The Epic branch starts from `origin/<branch>`, the Epic PR targets `<branch>`, and the finish compares against it, so the PR holds only this Epic's work. At the start and at the finish, the script merges `origin/<branch>` into the Epic branch when it is not there yet, so a fix KC pushes to the base reaches the work on top and none of it is thrown away. A merge that conflicts is aborted and stops the run, as does a base that is not on origin. When the base PR merges, KC retargets the stacked PR to `main` and merges `origin/main` into its branch. After a squash merge, that merge brings in the same changes the branch already has, so it is usually clean. Without `--on`, the Epic builds on `main_branch`.

## Settings

Each section names what it settles, and its `loop.toml` key when the script reads one. A repo's `docs/agents/loop.md` keeps these headings. A value with a key lives in `loop.toml` only, and the repo doc points there; the doc holds the values the script cannot read.

The machine README, `~/.local/share/chezmoi/README.md`, holds how to reach each machine and how secrets get onto it. Secrets and Hosts link to it.

### Run

Settles who starts a run, and where. The command is `loop start <Epic key>` in the main checkout, with `--on <branch>` to stack the Epic (rule 14), and `loop stop <Epic key>` stops it (rule 12). One run of a repo goes at a time on a host, because every Epic uses the same stack slots. Each host knows only its own units, so two hosts can both start a run on the same Epic. A person keeps it to one run at a time across hosts.

### Tracker

Settles the tracker and how the Epic's children and blocking edges are stored. `[tracker]` gives `kind` and `url`. Jira is the only adapter. It reads the children of an Epic as the issues with `parent = <Epic key>`, and a blocking edge as a "Blocks" issue link. It signs in with basic auth, the account email and an API token without scopes, on the site URL. It marks a stuck ticket with the Jira Flagged field, so the site needs that field. Set `name_landed_keys_only = true` when the tracker's automation closes each issue that a merged pull request names. The Epic PR then gives a ticket that did not land by its summary, not its key. The default is `false`.

### Status and stuck marker

Settles which status changes the loop makes, which the tracker's automation makes, and how a stuck ticket shows. `tracker.in_progress` and `tracker.landed` name the loop's statuses. Each must match a status name of the workflow exactly, and the workflow must offer a transition to it from the status that a ticket has at that point. The loop never sets the done status, because a landed ticket is on the Epic branch, not on `main`.

### Human steps

Settles what only a person can do, and how tickets carry it.

### Branches and commits

Settles where the key goes in commits. The script names each branch `feat/<KEY>-<slug>`, or `fix/` for a Bug. `main_branch` names the branch the Epic PR targets.

### Gates

Settles the ticket gate, the merge gate, and what CI runs. `[gates]` gives `ticket`, `merge`, and `timeout_minutes`. `agent_hint` adds a line to each ticket file for what the gate command does not say, such as what the tests need from the stack. A gate is an argument list that the script runs with no shell, so a pipe or `&&` in it does not work: put them in a script or a make target. The script gives a gate none of the repo's secrets (Secrets). A gate that needs the stack's secrets reads them from the secrets file through a repo script, and passes no others on.

### Acceptance tests

Settles how the loop knows that each line of what the user sees has a test. `[acceptance]` gives `list`, a command that prints the title of each acceptance test of a ticket, one per line, where each `{key}` names the ticket. The lines are the list under the heading `ACCEPTANCE_HEADING` in [`config.py`](../../loop/src/loop/config.py), "What the user sees", in the ticket text (rule 4). The repo's `docs/agents/testing.md` gives the suite, its command, and its rules. A repo with no acceptance suite leaves the table out.

### Stack per worktree

Settles how two tickets run full stacks side by side. `[stack]` gives the base `ports` and the `port_step` per slot, and the script sets `COMPOSE_PROJECT_NAME` to `<name>-<key>`. A repo with no stack leaves it out.
Slot 0 is the main checkout, so a person's own stack keeps the base ports. The Epic branch uses slot 1, and the tickets in flight use slot 2 and up, so the highest slot is `parallel` + 1. For each key under `ports`, the script sets an env var of that name to the slot's port, and the repo's Compose files and dev server configs read it.
Every Epic uses the same slot, so the slot ports must be free when a run starts. Before each gate and each agent run, the script reads `docker ps` for the containers of other Compose projects, such as a stack from a session outside the loop. When one holds a port of the slot, the slot moves to the first free spare slot after the ticket slots, `SPARE_SLOTS` in [`run.py`](../../loop/src/loop/run.py), for the rest of the run, and the script logs a `slot` line with the container. With no spare slot free, the ticket is stuck, and the reason names the container. At start, the script stops each `<name>-<key>` project that an earlier run left, and it stops the Epic stack when the run ends. Before each gate, it stops the stack of that gate, so the gate starts on new containers. A container from a failed start can start later with no published port. The volumes stay.

### UI review

Settles the UI paths, the review skill, the browser, sign-in, and what the review checks. `[ui]` gives `path`, `skill`, and `accepted_unchecked`: phrases for the parts that the review is known not to check, such as a list longer than the seed gives (rule 5). `path` is one folder prefix, and a changed file counts when its path starts with it. A file named `*.test.*` or `*.spec.*`, or under `__tests__/`, never counts. The skill is a skill of the repo, and the script gives it the run folder in the `LOOP_RUN_DIR` env var and in its prompt. A repo with no UI leaves it out, and the UI gate never fires.

### Demo

Settles the always-on demo that KC opens to review the Epic. `[demo]` gives `command` and `url`, and both are required. At the finish, after the push, the script runs `command` in the Epic worktree, with each `{branch}` replaced by the Epic branch, under the gate timeout. Its output goes to `finish-demo.log` in the run folder. When it passes, the Epic PR starts with `**Demo:**` and the `url`. When it fails, the PR is a draft that names the command and its log (rule 10). A repo with no demo leaves it out.

### Agent

Settles what the head agent runs on. `[agent]` gives `model` and `effort`, and the defaults are `claude-opus-5-5` and `high`. Effort is the setting to change to cut cost: at every cost, Opus 5.5 scores at or above Sonnet 5.5. Every agent run compacts at `CONTEXT_TOKENS` in [`config.py`](../../loop/src/loop/config.py), 200000 tokens, passed as `--autocompact`. Each turn sends the whole context again, so the cost of a ticket grows with how large its sessions get: in the last Epic run, sessions that reached 190K to 330K tokens cost two to three times as much per turn as sessions under 110K.

### Connectors

Settles which MCP servers the agent gets. When the repo has a `.mcp.json`, every agent run gets its servers and no other: no plugin server and no claude.ai connector of the host. Each server adds its tool names and instructions to the context of every turn, and the ticket file already holds the ticket text, so a run needs no tracker connector. A repo without a `.mcp.json` leaves each run the host's servers.

### Notifications

Settles the channel, the events, and what a message may contain. `notify.url` is the ntfy server, and the `NTFY_TOPIC` secret is the topic. A message holds a key and a status only. Anyone who knows the topic can read the messages, so the topic is a secret.

### Secrets

Settles which secrets the loop needs and where each one lives. `[secrets]` maps each env var to its Bitwarden `item` and `field`. The script needs `JIRA_EMAIL`, `JIRA_API_TOKEN`, and `NTFY_TOPIC`, and passes every secret to each agent run as an env var. The gates and the stack commands do not get them.
`loop secrets` copies them from Bitwarden to `~/.local/state/<name>-loop/secrets.json`, with mode 600, so a run needs no unlock. Run it once per host, and again after a secret changes. The file is the only place a run reads secrets from, so a run never needs an unlock.

### Hosts

Settles which machines can run the loop and what each needs. The loop runs on Linux with systemd, and the user has linger on (`loginctl enable-linger`), so the units outlive the login. `tools` lists the commands the repo needs beyond the script's own.

### Limits

Settles the numbers in rule 8. `[limits]` gives `parallel`, `agent_timeout_minutes`, `fix_attempts`, and `circuit_breaker`. `parallel` is 1 by default.

### Logs

The worktrees, the run folders, and the logs go to `~/.local/state/<name>-loop/<Epic key>/`. The `name` in `loop.toml` also names the run units and prefixes the Compose projects.
`loop watch` serves a page of these logs. Its header names the project, the Epic, and the run's status, where a run is running when `systemctl --user is-active` says its unit is: running; paused, while the integrator waits for a usage limit to reset, with the time the run resumes; completed, when the Epic PR is open or every ticket is complete; failed, when the loop itself failed; blocked, when a ticket is stuck or the run stopped for want of a ticket it could land; stopped, also when the run has no end line because it was killed; or idle. The overview shows the tickets complete of the Epic's total, where a ticket is complete when it landed on the Epic branch or was done in the tracker before; the plan meter of each window with its reset time; the work queue; and the screenshots. The meter is the newest reading on the host: a running agent's `meter` line gives one at most a minute old, and an agent line gives the one at the agent's end. With no reading, the page says so, and never derives one from the dollar cost. The work queue shows each running ticket with its step, the one whose `started` line has no result yet (build, ticket gate, code review, UI review, land), how long it has run, its last tool call, and its health: blocked while it waits for the usage limit; needs attention when its agent has written nothing for 15 minutes, or its ticket gate failed since it last passed; on track otherwise. After a kill or a stop, each ticket that was in a step shows as stopped, with that step. Below come the stuck tickets, then the tickets that wait to start, in the order the loop takes them: the ready ones by key, then each one after its blockers, and last the ones behind a stuck ticket. The screenshots are a running ticket's, or else the newest, marked with what the UI review made of them: passed, faults, passed with faults left unfixed, or not reviewed yet when no UI review line follows them. A viewer pages through each ticket's screenshots. The Tickets view lists every ticket, and a ticket opens its detail: its blockers, its step, its gate failures, each agent run as one line per tool call, the steps with their gate logs, the screenshots, and the files. Each tool call that auto mode denied shows in red. The Diagnostics view gives the same for the whole run. The Usage view gives the meter in full, the share of each window this run used, in percent, and that share per landed ticket, how many more tickets fit in the rest of each window at that rate once a ticket has landed, the first-pass rate (the share of the tickets landed in this run that passed their first ticket gate), the median time from a ticket's start to its landing, and the cost against the run before. The page reads `board.json`, which the script writes each time it reads the frontier, so the page needs no tracker. One page serves every project on the host: each `<name>-loop` folder next to the state folder is a project, and each API path takes `?project=<name>`. The bare address opens the home page, from `/api/home`, which the project and Epic menus read too. It gives the number of runs on the host now, the plan meter, and a panel for each project. Each panel lists the latest run of each Epic, the running one first, with its status, its tickets complete of the total, each running ticket with its step, and the time of its last step. A run opens its Epic. The house icon in the top bar opens the home page from every view. It masks the value of each secret in every project's secrets file. The page polls every 3 seconds, redraws what changed, and reloads itself when the page on disk changes. It follows the look of the Pitchridge design system, and lays out as one column with a floating tab bar on a phone and as two columns from 1024 px. It listens on localhost and on the host's tailnet address, at port 8790, `WATCH_PORT` in [`config.py`](../../loop/src/loop/config.py). It answers only a request whose Host is localhost, the tailnet address, or the MagicDNS name, in full or as the host name alone, and gives 403 to any other, because a site whose name resolves to the host (DNS rebinding) sends its own name. It has no auth and no Origin check. The project whose `loop.toml` started the page has a Start a run button in its home panel while no run of the project is active, and a Stop button on the active run's view. While no run is active, a run view has a Resume button, which starts its own Epic again, when the board has a ticket that is not complete, and a Start another Epic button otherwise. Start lists the open Epics of the Jira projects whose Epics ran on the host, from `/api/start`, with the same Jira read as the forecast, and a POST to `/api/start/<Epic key>` starts the one picked. A ticket is open when Jira has it open and not in the landed status. Each Epic is ready when it has open tickets and never ran on the host, resume when it ran before and has open tickets, landed when it has tickets and none is open, so a run opens the Epic PR, or no tickets, which Start does not offer until `/to-tickets` writes them. The ready and resume Epics come first. Stop asks to confirm, and a POST to `/api/stop/<Epic key>` returns when the run has ended (rule 12). The other projects on the page get no button. On a phone the button sits beside the large title, because the top bar has no room for it. `loop start` runs it as the user service `loop-watch-8790` (rule 12), and restarts it when it takes new commits, so the reloaded page never meets an older API. The page and its JSON API, such as `/api/epic/<Epic key>` and `/api/usage`, serve a person and an agent alike.
`loop report [<Epic key>]` breaks down what the Epic's latest run cost, or the latest run on the host. The cost that counts is the plan meter: the share of each window the run used, in percent, and that share per landed ticket. For each window, which one reset time names, the run used the highest `end` less the lowest `start` of its agent lines. The report then gives what drives the head agent's cost, per ticket it worked on: its turns, its peak context, and its hand-offs to each subagent tier. The dollar figures follow, labelled `list price (API)`, because they are what the API would bill and not what the plan costs: by role (the head agent with its subagents, the reviews, the PR body), by model, and by subagent, with the tickets landed and stuck, the review findings, and the Haiku cost above its 100K-token prompt rate. It compares each figure with the run before it on this host, or with the latest run of `--against <Epic key>`, and `--json` prints the same as JSON. The page shows it in its Usage view, from `/api/report/<Epic key>`.

The Usage view ends with a capacity forecast, a closed panel that reads data only while it is open, from `/api/forecast`. It is for planning only. No run reads it, no agent sees it, and it never writes to Jira. When the page asks, `loop watch` reads the open Epics of each Jira project with a run on the host, with their tickets' keys and statuses, but not their text, and keeps the read, or the error of a failed one, for `BACKLOG_MINUTES` in [`config.py`](../../loop/src/loop/config.py), 5 minutes. `[watch]` `plans` lists the Claude plan from each time on, such as `{ plan = "max-5x", since = 2026-10-14T16:30:00Z }`; the plans are `pro`, `max-5x`, and `max-20x`, and [`forecast.py`](../../loop/src/loop/forecast.py) holds Anthropic's multiple and monthly price for each. A `since` with a date only leaves the runs of that day unclear, as is a run that a change falls inside. Open work gives one row per open Epic, with its tickets left and the share of a 5-hour and a weekly window they need. A ticket is left when Jira has it open, not in the landed status, and no run on the host landed it. An Epic with no tickets yet has none to count. The share one ticket needs of each window is the current plan's own runs' share over their landed tickets, and a run that landed nothing counts toward it, since its work went into tickets that landed later. Capacity gives the tickets that fit in a 5-hour window and in a week at that share, the weeks the open work needs, and the same for each bigger plan, scaled by its multiple, with its extra monthly price. Plans compared sets the plans side by side, run by run: the runs, the tickets landed, the first-pass rate, the fix rounds per landed ticket (failed ticket gates, failed merge gates, code reviews with findings, and UI reviews with faults), the tickets stuck, the median time to land less the waits for a usage limit, and the limits hit, each counted once however many runs waited for its reset.
[`/check-loop`](../check-loop/SKILL.md) reads this design, the repo's settings, and the run's logs, and tells KC in a few lines what is wrong, the proper fix, and whether it needs KC or an agent can make it.
