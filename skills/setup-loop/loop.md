# The loop

A script builds one Epic unattended. It reads the ticket graph from the tracker, starts an agent for each ticket on the frontier, runs the gates itself, and lands each green ticket on the Epic branch. No model decides what runs next or whether a ticket passed. KC merges the Epic PR into `main`.

This file is the one home of the fixed design. The `loop` command, from `loop/` in the agent-workflow repo, is the script for every repo. A repo's `loop.toml` holds the values the script reads, and its `docs/agents/loop.md` links here and holds the rest of its settings.

## Fixed design

Every repo keeps these rules. Change a rule here, on purpose, and give the reason in the pull request.

1. **Frontier.** A ticket is on the frontier when it is open, not stuck, and each of its blockers is done in the tracker or landed on the Epic branch. A ticket has landed when `git log <epic-branch> --grep "(<KEY>)"` finds its merge. The tracker and git hold all state, so the script keeps no state file. A ticket that is done in the tracker but whose branch holds work on neither main nor the Epic branch is not built. The script notifies at start and marks it in the Epic PR.
2. **Worktree.** Each ticket gets a worktree and a branch off the Epic branch, its own stack, and a ticket file outside the repo. The ticket file holds the ticket text and names the gate command that checks the work, which the agent makes pass before it returns `done`: the ticket gate. It also holds the comments on the ticket, without the loop's own stuck and decisions comments, which the script knows by their first line. When the comments cannot be read, the script logs it and writes the ticket file without them. When a remote branch already carries the key, the script uses that branch, and the ticket starts as a restart (rule 9). The script pushes the ticket branch after every agent run. Claude Code makes the worktree of a `trial` subagent under `.claude/worktrees/` in the main checkout, and removes it when the trial leaves no change. After every agent run, the script also removes the trial worktrees that run left, with their branches: each one that is not locked and whose commit is on the ticket branch but not on main.
3. **Agent run.** For a ticket, the script runs `claude -p` with `/implement` and the ticket file as the prompt. [`EpicRun.agent`](../../loop/src/loop/run.py) holds the whole command, and every agent run, for a ticket or for the finish, gets these parts:
   - `timeout` with `--kill-after` stops the run and every process it started at the agent timeout, and kills what still runs a minute later.
   - A session that has returned its status and has not exited 2 minutes later is stopped, as a background task, such as a dev server, keeps `claude -p` open until the task ends. A late turn within those 2 minutes still counts.
   - `--permission-mode auto` and `--permission-prompts none` let the run go on with nobody there to answer a prompt.
   - `--output-format stream-json` with `--verbose` writes each event to the agent log as it happens, so a run can be followed while it lasts.
   - `--json-schema` makes the run return its status in a fixed shape.
   - `-n` names the session after the ticket key.
   - `--mcp-config` gives the run the worktree's `.mcp.json` when it has one, because nobody approved the project's MCP servers in a new worktree folder. `--strict-mcp-config` then gives the run only those servers (Connectors).
   - `--agents` gives the loop's subagent tiers, which [`tiers.py`](../../loop/src/loop/tiers.py) reads from the files in [`agents/`](../../agents). `install.sh` links the same files into `~/.claude/agents`. `--append-system-prompt` adds the rule for when to hand work to them in [`dispatch.md`](../../loop/src/loop/dispatch.md). A run of `implement` outside the loop gets the tiers, and not the rule.
   - `--settings` gives the rules of [`agent_settings`](../../loop/src/loop/run.py): the gate commands run without the classifier, and the classifier learns that the `<name>-<key>` stacks are the loop's own, so an agent can stop one to free a port. `worktree.baseRef` is `head`, so a `trial` worktree branches from the ticket's last commit rather than from main. No agent run deletes a volume. Nobody answers a prompt in a run, so a routine action that auto mode denies makes a ticket stuck.
   - `--resume` continues the session for a fix attempt.
   - `--autocompact` sets the window that every run compacts at, `[agent]` `context_tokens` (Agent).
   - `--model` and `--effort` run the review sessions of rules 4 and 5 on `REVIEW_MODEL` at `REVIEW_EFFORT` in [`run.py`](../../loop/src/loop/run.py). Every other run, the head agent's sessions and the PR body, runs on the model and effort of `[agent]` (Agent), so no run takes them from the host's own Claude Code settings.

   The schema returns `status` (`done` or `blocked`), `reason`, and `decisions`, the judgement calls for KC to check. The script comments the decisions on the ticket and lists them in the Epic PR. Each turn ends with a result event, and the script takes the status from the last result event that has one. A `blocked` status makes the ticket stuck. Claude Code asks for the status as soon as a turn ends, so a head agent that ends its turn to wait for a background subagent gives its status too early. A `blocked` status given while subagents still ran resumes the session once with a prompt to continue, and a second `blocked` stands. `dispatch.md` therefore names `run_in_background: false`, because an Agent call without it starts the subagent in the background.

4. **Ticket gate and code review.** The script runs the ticket gate in the worktree. When it fails, the script resumes the session with the tail of the log, up to the fix attempt limit. Still failing, the ticket is stuck. Every gate runs under `timeout` with `--kill-after`, as the agent does, with the gate timeout as its limit, so a gate past its limit fails and its child processes stop with it. When the gate first passes on a ticket, the script runs `/code-review` against the Epic branch in a new session. The review returns the findings that need a change, which are the breaks of the behaviour, the ticket, or a documented standard, and it lists polish that blocks nothing in `decisions`, after every subagent it started has returned, as its result ends the session. The script resumes the head agent's session to fix them, and the ticket gate runs again. This fix is not a fix attempt. A ticket gets one code review: the script marks it done in the run folder, so a restart does not run it again, and a restart before the fix carries the findings in its prompt. The ticket file tells the head agent that the loop runs the reviews.
5. **UI gate.** When the diff against the Epic branch touches a UI path, the script runs the UI review skill in a new session after the code review. The review saves its screenshots in the run folder and returns each fault it sees. A fault goes back to the head agent's session, which is not a fix attempt, and the new commit gets a new UI review. A fault still there after one such fix does not stick the ticket: it lands, and the fault goes to KC as a decision on the ticket and the Epic PR. A part that the environment cannot show, such as a screen that needs a bucket name, is not a block: the review lists it in `decisions`, and the Epic PR carries it for KC to review by hand. A review that is blocked, or that saves no screenshots, makes the ticket stuck. The script records the commit that the screenshots show, in `ui-review.commit` in the run folder, and keeps the screenshots while the ticket's own change to the UI paths stays what that commit had, so a later commit with no UI change, or a merge of the Epic branch, gets no new UI review. The script attaches the screenshots to the ticket.
6. **Land.** Merges run one at a time: `git merge --no-ff` into the Epic branch, with the key in the message, then the merge gate on the Epic branch. When the gate passes, the Epic branch takes the merge and the script pushes it. A failed push is logged, and the run goes on. A conflict or a failed merge gate undoes the merge. The script then merges the Epic branch into the ticket branch, removes the ticket's database volume so that the migrations the merge brought in run from the start, and resumes the session as a fix attempt, to resolve the conflict or to fix the cause from the tail of the gate log. Out of fix attempts, the ticket is stuck.
7. **Stuck.** The script sets the stuck marker on the ticket, comments the reason and the log path, and notifies. Other frontier tickets keep running. Tickets downstream of a stuck one wait.
8. **Limits.** Parallel tickets, the agent timeout, and fix attempts per ticket cap the work. A run of stuck tickets in a row as long as the circuit breaker stops the loop. A usage limit that resets within 6 hours pauses the session: the script notifies, waits for the reset that the run's `rate_limit_event` gives, and resumes the session. Any other usage limit stops the loop and notifies.
9. **Restart.** The script keeps each in-progress ticket's branch and starts a fresh agent with "A previous run was interrupted. Check the diff against the ticket and continue." The restart counts as a fix attempt.
10. **Finish.** When the frontier is empty and nothing runs, the script runs the merge gate on the Epic branch, pushes it, and opens the Epic PR. It runs no review, because each ticket got its code review at landing (rule 4), and the review of the whole Epic is KC's. An agent writes the PR body with the `pr` skill. Without a body from it, the body is the ticket table. If a gate still fails, or a ticket is stuck, not built, or done in the tracker but not landed, the PR is a draft. The failing gate and the unfinished tickets go at the top, because a merge of the Epic PR can close the Epic and all of its children in the tracker. Then it notifies.
11. **Log.** One JSONL line per decision, with the ticket, step, result, commit, and session id, in the log folder outside the repo. Each agent line adds `usage`, from the run's last result event: `total_cost_usd`, `num_turns`, `duration_ms`, the subagents by type, and the usage of each model. A resumed session reports the cost and the models of the whole session so far, so the last agent line of a session holds its total. `usage` also gives `peak_context`, the largest context that one of the session's own assistant messages sent: its input, cache read, and cache write tokens. Each agent line adds `plan`, the Claude plan meter over the run from its `rate_limit_event` lines: for each of `five_hour` and `seven_day`, the first and the last utilization as `start` and `end`, and `resets_at`. A run that meets a usage limit logs its agent line too, with the result `usage-limit`. The meter belongs to the account, so parallel runs and KC's own sessions move it together, and `loop report` counts it per Epic run, not per ticket (Logs). The Epic's start line adds `setup`: the `claude` version, and the model and effort of the head agent, of each subagent tier, and of the reviews, so two runs can be told apart.
12. **Host.** The script checks every prerequisite before it starts and refuses to run when one is missing. A `claude` older than `MIN_CLAUDE` in [`run.py`](../../loop/src/loop/run.py) counts as missing, because it does not know every model the tiers name. It holds off sleep for the run, with `systemd-inhibit` on Linux and `caffeinate` on macOS. `loop start` first fast-forwards the loop's own clean checkout of agent-workflow to origin, so every host runs the merged loop, and refuses when it cannot. When it takes new commits, it restarts on the new code before it reads `loop.toml`. It then runs the loop in its own tmux session, so the run outlives the agent or shell that starts it. When the run has started, it opens the `loop watch` page (Logs) and prints its tailnet address, which opens on any device in the tailnet. An agent starts a run only with `loop start`, because the Bash tool stops a command after 10 minutes.
13. **Main.** The loop lands work only on the Epic branch. KC merges the Epic PR.
14. **Stacked Epic.** `loop start <Epic key> --on <branch>` builds the Epic on a branch of origin that is not merged yet, such as the branch of the previous Epic's PR, so the next Epic can run while KC has not reviewed the last. The Epic branch starts from `origin/<branch>`, the Epic PR targets `<branch>`, and the finish compares against it, so the PR holds only this Epic's work. At the start and at the finish, the script merges `origin/<branch>` into the Epic branch when it is not there yet, so a fix KC pushes to the base reaches the work on top and none of it is thrown away. A merge that conflicts is aborted and stops the run, as does a base that is not on origin. When the base PR merges, KC retargets the stacked PR to `main` and merges `origin/main` into its branch. After a squash merge, that merge brings in the same changes the branch already has, so it is usually clean. Without `--on`, the Epic builds on `main_branch`.

## Settings

Each section names what it settles, and its `loop.toml` key when the script reads one. A repo's `docs/agents/loop.md` keeps these headings. A value with a key lives in `loop.toml` only, and the repo doc points there; the doc holds the values the script cannot read.

The machine README, `~/.local/share/chezmoi/README.md`, holds how to reach each machine and how secrets get onto it. Secrets and Hosts link to it.

### Run

Settles who starts a run, and where. The command is `loop start <Epic key>` in the main checkout, with `--on <branch>` to stack the Epic (rule 14).

### Tracker

Settles the tracker and how the Epic's children and blocking edges are stored. `[tracker]` gives `kind` and `url`. Jira is the only adapter. Set `name_landed_keys_only = true` when the tracker's automation closes each issue that a merged pull request names. The Epic PR then gives a ticket that did not land by its summary, not its key. The default is `false`.

### Status and stuck marker

Settles which status changes the loop makes, which the tracker's automation makes, and how a stuck ticket shows. `tracker.in_progress` and `tracker.landed` name the loop's statuses.

### Human steps

Settles what only a person can do, and how tickets carry it.

### Branches and commits

Settles where the key goes in commits. The script names each branch `feat/<KEY>-<slug>`, or `fix/` for a Bug. `main_branch` names the branch the Epic PR targets.

### Gates

Settles the ticket gate, the merge gate, and what CI runs. `[gates]` gives `ticket`, `merge`, and `timeout_minutes`. `agent_hint` adds a line to each ticket file for what the gate command does not say, such as what the tests need from the stack.

### Stack per worktree

Settles how two tickets run full stacks side by side. `[stack]` gives the base `ports` and the `port_step` per slot, and the script sets `COMPOSE_PROJECT_NAME` to `<name>-<key>`. A repo with no stack leaves it out.
Every Epic uses the same slot, so the slot ports must be free when a run starts. At start, the script stops each `<name>-<key>` project that an earlier run left, and it stops the Epic stack when the run ends. Before each gate, it stops the stack of that gate, so the gate starts on new containers. A container from a failed start can start later with no published port. The volumes stay.

### UI review

Settles the UI paths, the review skill, the browser, sign-in, and what the review checks. `[ui]` gives `path` and `skill`. A repo with no UI leaves it out, and the UI gate never fires.

### Agent

Settles what the head agent runs on. `[agent]` gives `model` and `effort`, and the defaults are `claude-opus-5-5` and `high`. Effort is the setting to change to cut cost: at every cost, Opus 5.5 scores at or above Sonnet 5.5. `context_tokens` is the window that every agent run compacts at, passed as `--autocompact`, and it defaults to 200000. Each turn sends the whole context again, so the cost of a ticket grows with how large its sessions get: in the last Epic run, sessions that reached 190K to 330K tokens cost two to three times as much per turn as sessions under 110K.

### Connectors

Settles which MCP servers the agent gets. When the repo has a `.mcp.json`, every agent run gets its servers and no other: no plugin server and no claude.ai connector of the host. Each server adds its tool names and instructions to the context of every turn, and the ticket file already holds the ticket text, so a run needs no tracker connector. A repo without a `.mcp.json` leaves each run the host's servers.

### Notifications

Settles the channel, the events, and what a message may contain. `notify.url` is the ntfy server, and the `NTFY_TOPIC` secret is the topic.

### Secrets

Settles which secrets the loop needs and where each one lives. `[secrets]` maps each env var to its Bitwarden `item` and `field`. The script needs `JIRA_EMAIL`, `JIRA_API_TOKEN`, and `NTFY_TOPIC`, and passes every secret to each agent.
`loop secrets` copies them from Bitwarden to `~/.local/state/<name>-loop/secrets.json`, with mode 600, so a run needs no unlock. Run it once per host, and again after a secret changes. A run reads Bitwarden only when the file is missing.

### Hosts

Settles which machines can run the loop and what each needs. `tools` lists the commands the repo needs beyond the script's own.

### Limits

Settles the numbers in rule 8. `[limits]` gives `parallel`, `agent_timeout_minutes`, `fix_attempts`, and `circuit_breaker`.

### Logs

The worktrees, the run folders, and the logs go to `~/.local/state/<name>-loop/<Epic key>/`. The `name` in `loop.toml` also names the tmux session and prefixes the Compose projects.
`loop watch` serves a read-only page of these logs. Its header names the project, the Epic, and the run's status: running; paused, when every running ticket waits for the usage limit; completed, when the Epic PR is open or every ticket is complete; failed, when the loop itself failed; blocked, when a ticket is stuck or the run stopped for want of a ticket it could land; stopped; or idle. The overview shows the tickets complete of the Epic's total, where a ticket is complete when it landed on the Epic branch or was done in the tracker before; the plan meter of each window with its reset time; the work queue; and the screenshots. The meter is the newest reading on the host: the running agent's log gives one minutes old, and an agent line gives the one at the agent's end. With no reading, the page says so, and never derives one from the dollar cost. The work queue shows each running ticket with its step (agent, ticket gate, code review, UI review, land), how long it has run, its last tool call, and its health: blocked while it waits for the usage limit; needs attention when its agent has written nothing for 15 minutes, or its ticket gate failed since it last passed; on track otherwise. Below come the stuck tickets, then the tickets that wait to start, in the order the loop takes them: the ready ones by key, then each one after its blockers, and last the ones behind a stuck ticket. The screenshots are a running ticket's, or else the newest, marked with what the UI review made of them: passed, faults, passed with faults left unfixed, or not reviewed yet when no UI review line follows them. A viewer pages through each ticket's screenshots. The Tickets view lists every ticket, and a ticket opens its detail: its blockers, its step, its gate failures, each agent run as one line per tool call, the steps with their gate logs, the screenshots, and the files. Each tool call that auto mode denied shows in red. The Diagnostics view gives the same for the whole run. The Usage view gives the meter in full, the share of each window this run used, in percent, and that share per landed ticket, how many more tickets fit in the rest of each window at that rate once a ticket has landed, the first-pass rate (the share of the tickets landed in this run that passed their first ticket gate), the median time from a ticket's start to its landing, and the cost against the run before. The page reads `board.json`, which the script writes each time it reads the frontier, so the page needs no tracker. One page serves every project on the host: each `<name>-loop` folder next to the state folder is a project, and each API path takes `?project=<name>`. It masks the value of each secret in every project's secrets file. The page polls every 3 seconds, redraws what changed, and reloads itself when the page on disk changes. It follows the look of the Pitchridge design system, and lays out as one column with a floating tab bar on a phone and as two columns from 1024 px. It listens on localhost and on the host's tailnet address, at `[watch]` `port`, which is 8790 by default. `loop start` starts it in the `<name>-watch` tmux session when nothing answers on the port. The page and its JSON API, such as `/api/epic/<Epic key>` and `/api/usage`, serve a person and an agent alike.
`loop report [<Epic key>]` breaks down what the Epic's latest run cost, or the latest run on the host. The cost that counts is the plan meter: the share of each window the run used, in percent, and that share per landed ticket. For each window, which one reset time names, the run used the highest `end` less the lowest `start` of its agent lines. The report then gives what drives the head agent's cost, per ticket it worked on: its turns, its peak context, and its hand-offs to each subagent tier. The dollar figures follow, labelled `list price (API)`, because they are what the API would bill and not what the plan costs: by role (the head agent with its subagents, the reviews, the PR body), by model, and by subagent, with the tickets landed and stuck, the review findings, and the Haiku cost above its 100K-token prompt rate. It compares each figure with the run before it on this host, or with the latest run of `--against <Epic key>`, and `--json` prints the same as JSON. The page shows it in its Usage view, from `/api/report/<Epic key>`.

The Usage view ends with a capacity forecast, a closed panel that reads data only while it is open, from `/api/forecast`. It is for planning only. No run reads it, no agent sees it, and it never writes to Jira. `loop watch` reads the open Epics of each Jira project with a run on the host, with their tickets' keys, titles, statuses, and blockers, but not their text. It reads them every `[watch]` `backlog_minutes` (5 by default), and when the page asks with a POST to `/api/forecast/refresh`. It keeps the last read in `backlog.json` in the state folder, so a failed read or a restart keeps the last snapshot, and the page shows its age, the error, and that it is stale after two missed reads. `[watch]` `plans` lists the Claude plan from each time on, such as `{ plan = "max-5x", since = 2026-10-14T16:30:00Z }`; the plans are `pro`, `max-5x`, and `max-20x`, and [`forecast.py`](../../loop/src/loop/forecast.py) holds Anthropic's multiple and monthly price for each. A `since` with a date only leaves the runs of that day unclear, as is a run that a change falls inside. The forecast compares the plans run by run: the tickets landed, the first-pass rate, the ticket gate failures, the stuck tickets, the median time to land less the waits for a usage limit, those waits, and each window's share per landed ticket in that plan's own percent, with the 5-hour share also in Pro windows by the multiple. It estimates the share one ticket needs from the current plan's runs, or, until that plan has 5 landed tickets under a meter reading, from every plan's runs scaled by the multiple, and gives the lowest and the highest run with it. A ticket is left when Jira has it open, not in the landed status, and no run on the host landed it; an Epic with no tickets yet is named and left out. The plan limits the loop when a 5-hour window fits fewer tickets by usage than the loop lands in 5 hours of its median time. Each higher plan shows its extra monthly price and the gain the loop's time allows. Until the plan has 5 landed tickets, the forecast says it is preliminary and names the evidence still to collect.
[`/check-loop`](../check-loop/SKILL.md) reads this design, the repo's settings, and the run's logs, and tells KC in a few lines what is wrong, the proper fix, and whether it needs KC or an agent can make it.
